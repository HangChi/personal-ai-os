# Feature Specification: 阶段 17 — 跨模块全局搜索

**Feature Branch**: `017-global-search`

**Created**: 2026-10-25

**Status**: Draft

**Input**: 用户需求：「继续跨模块全局搜索，跨模块你有哪些建议」。

## 背景

数据分散在五个模块（任务、对话、日程、记忆、知识库），每个模块有自己的列表和筛选，
但**没有一处能回答「那个东西在哪」**。

实际场景：记得「曾经让助手记过一件关于教材的事」，但不记得它在哪个会话、哪个任务、
还是记忆页。现在的做法是逐个模块翻 —— 而这正是搜索应该消除的成本。

阶段 16 已给会话与知识库补了列表搜索，但那是**模块内**搜索；本阶段做的是**跨模块**。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一处搜索，按模块分组看到结果（Priority: P1）

作为用户，我在顶栏输入关键词，结果页按模块分组展示命中条目，点一条直接跳到对应页面。

**Why this priority**：这是本阶段的全部价值。

**Independent Test**：在五个模块各造一条含同一关键词的数据 → 搜索该词 →
结果页出现五个分组，每组一条，点击任一分类目能跳转。

**Acceptance Scenarios**：

1. **Given** 五个模块都有命中，**When** 搜索，**Then** 结果按模块分组展示，每组显示模块名与条数。
2. **Given** 点击某条命中，**When** 跳转，**Then** 到达对应模块页面并带上该条目标识。
3. **Given** 某模块没有命中，**When** 查看结果，**Then** 该分组**不出现**（不是显示「0 条」占位）。
4. **Given** 关键词在多个字段命中，**When** 查看条目，**Then** 能看到命中的是哪个字段
   （标题 / 描述 / 地点 / 内容 / 文件名）。

---

### User Story 2 - 命中消息内容时返回会话（Priority: P1）

作为用户，我搜一句「曾经说过的话」，结果给出**那个会话」，而不是散落的多条消息。

**Why this priority**：消息与片段量级大，直接作为结果会让一次搜索返回几百条。

**Independent Test**：在某会话里发一条含唯一词的消息 → 搜索该词 → 结果里出现该会话，
且标注命中的是「消息内容」。

**Acceptance Scenarios**：

1. **Given** 某会话的消息正文含关键词（标题不含），**When** 搜索，**Then** 结果包含该会话，
   标注字段为「消息内容」。
2. **Given** 同一会话既有标题命中又有消息命中，**When** 搜索，**Then** 该会话只出现一次，
   标注为「标题」（标题命中优先）。
3. **Given** 某文档的分块含关键词（标题不含），**When** 搜索，**Then** 结果包含该文档，
   标注字段为「正文」。

---

### User Story 3 - 单个模块故障不拖垮整个搜索（Priority: P2）

作为用户，即使某个模块查询出错，我也应该看到其他模块的结果。

**Why this priority**：聚合查询的失败模式是「一个模块挂 → 整个搜索白屏」，
而用户此时最需要的是其他模块的结果。

**Acceptance Scenarios**：

1. **Given** 其中三个模块有命中、一个模块查询抛异常，**When** 搜索，
   **Then** 返回另外三个模块的结果（HTTP 200），故障模块的分组缺失。
2. **Given** 全部模块无命中，**When** 搜索，**Then** 返回空结果与明确提示，不是错误。

## Edge Cases

| 输入 | 期望行为 |
|---|---|
| 关键词为空或纯空白 | `40000`（而不是返回全部数据 —— 那等于一次全库导出） |
| 关键词只有 1 个字符 | 允许，但可能命中极多；由每模块 limit 兜住 |
| 关键词含 SQL 通配符（`%`、`_`） | 按字面匹配，不当作通配符 |
| 关键词超长（>100 字符） | `40000`，提示长度上限 |
| 某模块数据量为 0 | 该分组不出现，不影响其他模块 |
| 同一会话被多个消息命中 | 该会话只出现一次 |
| 搜索词在标题与内容同时命中 | 标题优先标注 |

## Requirements *(mandatory)*

- **FR-001**：MUST 提供 `GET /api/v1/search`，入参 `keyword` 与 `limit`（每模块条数，默认 5）。
- **FR-002**：MUST 覆盖五个模块：任务（标题/描述）、会话（标题/消息内容）、
  日程（标题/描述/地点）、记忆（内容）、知识库（标题/文件名/分块内容）。
- **FR-003**：搜索结果 MUST 按模块分组，每组含模块名、条数、命中条目；无命中的模块不出现。
- **FR-004**：每条命中 MUST 标注命中的字段名。
- **FR-005**：标题类字段的命中 MUST 优先于正文类字段的命中（同一对象两类都命中时）。
- **FR-006**：MUST 通过 SPI（`SearchContributor`）让各模块提供自己的搜索实现，
  MUST NOT 在聚合服务里 import 五个模块的 Service。
- **FR-007**：单个模块搜索失败 MUST NOT 导致整个请求失败。
- **FR-008**：返回的条目 MUST 带 `kind` 与 `id`，由**前端**映射跳转路由
  （后端不得知道前端路由表）。
- **FR-009**：每模块返回条数 MUST 有上限（`limit`，最大 20）。
- **FR-010**：本阶段 MUST NOT 实现：搜索历史、关键词高亮、全文索引（`tsvector` / `pg_trgm`）、
  拼音与模糊匹配。理由见 Assumptions。

## Success Criteria

- **SC-001**：`./mvnw -B verify` 全绿；新增测试覆盖五模块命中、分组结构、
  标题优先于内容、单模块失败隔离、空关键词 400、limit 收敛。
- **SC-002**：`npm run test:logic` 全绿，覆盖「kind → 路由」映射与空态文案。
- **SC-003**：真机：顶栏搜索 → 结果页分组展示 → 点击跳转到对应模块。

## Assumptions

- **不做全文索引**：个人量级（百级条目）下 `LIKE` 足够；引入 `tsvector` / `pg_trgm`
  需要新迁移、GIN 索引与不同的查询语法，而收益要等数据量上到万级才显现。
  真到了那个量级，正确做法是上独立搜索引擎，而不是在 Postgres 里加更多索引。
- **不做关键词高亮**：高亮要在前端对用户输入做 HTML 转义后再插标记，
  这一步做错就是 XSS。首版用「命中的字段」标注已经能解决「为什么是这条」。
- **不做搜索历史**：需要存储（存哪？保留多久？）与隐私考虑，
  而浏览器自己的历史已经能覆盖大部分「刚才搜过什么」。
- **不做拼音 / 模糊匹配**：需要额外的词典或 trigram 支持；
  中文场景下用户记住的通常是完整词，`LIKE` 的子串匹配已够用。
