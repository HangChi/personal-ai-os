# Research: 阶段 8 — 长期记忆

**Date**: 2026-10-25 | **Plan**: [plan.md](./plan.md)

## R-01 显式写入，不自动归纳

**Decision**：模型只在用户**明确要求记住**时调用 `saveMemory`；不做「每轮对话后自动提炼」。

**依据**：用户已选定该范式。补充理由：
- 自动归纳必然写入噪声（「用户问了天气」也会被记），而记忆是**全局注入**的，
  一条错误记忆会污染之后所有对话，且用户不知道它从哪来。
- 显式写入的每一次调用都对应一句用户原话，可解释、可撤销。

**被否决的方案**：
- **每轮自动摘要入库**：需要额外的模型调用（成本翻倍）、需要判断"什么值得记"（本质不可靠），
  且产生大量用户从未同意的条目。
- **自动写入候选 + 确认后入库**：最完备，但要复用确认机制、加一层候选状态，
  工作量约为显式方案的 2–3 倍，而用户已明确选择显式。

## R-02 单一内容字段，不做分类与标签

**Decision**：`memory` 表只有 `id / content / created_at / updated_at`。

**依据**：分类的唯一消费场景是「按类别注入」或「按类别检索」，本阶段两者都不做 ——
注入是全量（带预算），检索是"最近更新优先"。没有消费方的字段就是负债（宪法原则 I）。

**被否决的方案**：
- **`category` 枚举（偏好/事实/其他）**：模型要给每条记忆选类别，分类错了没人纠正；
  而界面上用户能直接读到原文，分类不增加信息。
- **`source_conversation_id` 溯源**：需要模型传会话标识（`ToolContext` 里有），
  但界面不展示来源、也不按来源过滤，纯记录。

## R-03 记忆不做向量化

**Decision**：不建 `vector` 列、不写 pgvector、不按相似度检索。

**依据**：本阶段设计的前提是「记忆总量几十条」。在此量级：
- 全量注入（30 条 / 6000 字符）对上下文的占用可接受；
- 向量检索要把「取最近 N 条」换成「取最相似 N 条」，而记忆的消费方式是**约束性事实**
  （「周报每周五交」），不是可被语义召回的资料——对话里没提到「周报」时，
  它**仍然应该生效**。相似度检索恰恰会在此时漏掉它。

**被否决的方案**：
- **pgvector + 相似度召回**：与「约束必须始终生效」的语义冲突，且几十条数据无收益。
- **关键词过滤**：同样会漏掉未被提及但必须遵守的记忆。

> 若将来记忆到几百条，正确方向是「分类 + 按类注入」或「分层（常驻 / 按需）」，
> 而不是相似度检索。

## R-04 注入走 `common/ai` 的 `PromptContributor` SPI

**Decision**：新增接口

```java
public interface PromptContributor {
    String contribute();   // 要追加到系统提示的文本；无内容返回空串
}
```

`memory` 模块实现它输出记忆块；`chat` 通过 `ObjectProvider<PromptContributor>` 收集。

**依据**：`ToolContributor` 的注释已经把架构理由写死了 ——
「chat 需要挂载各模块提供的能力，但它不应该依赖具体业务模块，否则会出现业务模块反向依赖对话模块，
而且每新增一类都要改动对话模块」。

记忆注入与工具挂载是同一类问题（chat 需要各模块贡献内容，但不该知道它们是谁）。
用同样的解法，架构才自洽。

**被否决的方案**：
- **`ChatCompletionService` 直接注入 `MemoryService`**：代码更短，但让 `chat` 依赖 `memory`，
  与上述注释正面冲突；且下次再有「天气上下文」「当前日程」这类注入需求时，
  chat 会被迫依赖越来越多的模块。
- **把记忆塞进 `JpaChatMemory.get()` 返回的历史消息里**：看起来巧妙（不动装配），
  但会让「历史消息」这个数据结构承载非历史内容，破坏语义；
  且 `ChatMemory.get()` 的窗口逻辑（按条数截断）会把记忆条也算进窗口，挤掉真实历史。

## R-05 注入预算：条数 + 字符双上限，且**不截断单条**

**Decision**：最多 30 条、累计不超过 6000 字符；按 `updated_at` 倒序累加，加入某条会超预算就**停止**。

**依据**：
- 只限条数不够：一条 2000 字的记忆 × 30 条 = 60000 字符，足以挤爆上下文。
- 只限字符不够：极短记忆（「好」）可以塞进几千条，噪音淹没信号。
- **不截断单条**：截断会产生语义残缺的约束（「我的周报每周五下午交，如果那天…」被砍掉后半句），
  比少注入一条危险得多 —— 残缺的约束会被模型当成完整约束执行。

**被否决的方案**：
- **按字符截断最后一条**：见上，残缺约束比缺失更危险。
- **按比例降采样**：用户无法预期哪些记忆生效，不可解释。

## R-06 去重：归一后逐字符相等即视为同一条

**Decision**：`saveMemory` 前先按 `content` 归一（strip）后精确比对已有条目；相同则不新增，返回既有条目。

**依据**：模型在长对话里很容易重复调用同一保存（用户连说两次「记住」）。
没有去重，10 轮对话下来表里会有 5 条一字不差的记忆，注入预算被同一件事吃光。

**被否决的方案**：
- **唯一索引**：`content` 是 `text`，PostgreSQL 对长文本建唯一索引可行但要求完全相等 ——
  与 Java 侧 `strip()` 后的比对口径不完全一致（库里的值是 strip 过的，所以等价）；
  真正的问题是**冲突要靠捕获异常处理**，把业务规则藏在 SQL 错误里。
  应用层先查后写在本量级足够，且能给出明确返回值。
- **语义去重（相似度阈值）**：需要嵌入模型，且阈值不可判定。

## R-07 `saveMemory` 不加人工确认

**Decision**：保存记忆直接执行，不进入 `confirmation` 流程。

**依据**：阶段 2 定下的确认边界是「删除 / 批量 / 关键字段」，保存记忆三者都不是：
不删除数据、单条、可撤销（界面上删掉即可）。要求确认会让「记住这个」变成两次交互。

**被否决的方案**：
- **走确认流程**：用户已经用自然语言明确说了「记住」，再弹一次确认属于重复询问。

## R-08 迁移 `V9__create_memory.sql`

**Decision**：新建 `memory` 表，一个迁移只做一件事。

```sql
CREATE TABLE memory (
    id         uuid PRIMARY KEY,
    content    text NOT NULL,
    created_at timestamptz NOT NULL,
    updated_at timestamptz NOT NULL
);
```

**依据**：宪法原则 IV。不建索引：几十行数据，`ORDER BY updated_at DESC` 走全表扫描即可；
给一张不会超过几百行的表加索引，是典型的形式主义优化。

**被否决的方案**：
- **给 `updated_at` 建索引**：本量级无收益，且索引也要占迁移与维护成本。
- **`content` 加长度 CHECK**：长度上限在 Service 层按「归一后长度」判定，
  与 007 的标题校验同一模式；在库里再写一个 `CHECK (length(content) <= 2000)` 会产生第二个口径。

## R-09 请求级 `system()` 覆盖默认系统提示，需显式拼上基础提示

**Decision**：`ChatCompletionService` 在每轮请求里调用
`.system(baseSystemPrompt + contributions)`，其中 `baseSystemPrompt` 取自 `AiProperties`。

**依据**：`ChatClient` 的 `defaultSystem` 是**默认值**，请求级 `system()` 会替换它。
若只传记忆块，阶段 1 定下的人格与行为约束会全部丢失 —— 这类错误不会报错，只会让助手"变了个样"。
因此必须显式包含基础提示，并由集成测试断言 SystemMessage 同时含基础提示与记忆块。

**被否决的方案**：
- **只传记忆块**：丢基础提示（见上）。
- **依赖 `defaultSystem` 自动追加**：Spring AI 不做拼接，行为是替换；依赖一个不存在的特性会静默失效。

**验证**：`MemoryIntegrationTest` 用桩模型断言 —— 有记忆时 SystemMessage 含基础提示**与**记忆块；
无记忆时 SystemMessage 与阶段 1 逐字符相同（SC-004）。
