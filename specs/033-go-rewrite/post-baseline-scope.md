## 为什么采用增量清单

`inventory.json`、`inventory.md` 和 `surface.md` 仍固定在
`cb5d694d62fa93742b5789b97273e76d931ce335`，不刷新原文件哈希，不把当前代码当作历史 oracle。
`scope-changes.json` 单独记录后续候选：原哈希、候选哈希、不可变源码提交、双端责任文件、测试依据和限制。
每个条目覆盖整个候选文件，包括新增类和工具；原声明索引继续只描述原基线。

普通 `go_inventory.py check` 验证冻结 oracle 和已登记增量的完整性。
未经登记的原文件改动、新文件、候选再次改动、任一双端责任文件漂移、与源码提交不符的哈希都失败；
原 SQL 不允许通过增量清单变更。实际 `.env`、本机数据和日志不在候选范围内。

`go_p8_inventory_progress.py` 对受影响的原基线文件取消继承完成状态，按增量状态列入待验收；
新增文件由增量清单逐文件覆盖。未受影响的原基线处置不变。登记范围不等于通过验证。
`check-complete` 必须同时满足原声明、增量验证和五项发布门禁。
将增量标为 `verified` 必须提供绑定原基线、源码提交、全部候选及双端责任哈希的 JSON 验证报告和检查列表，
并不能仅靠修改状态或重新计算哈希解除发布门禁。
