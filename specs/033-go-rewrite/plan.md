# Go 迁移方案

## 目标结构

保留现有 `backend/`，新增独立 `backend-go/`。Go 采用一个模块、一个应用入口、按业务组织的内部包；通过运行角色控制 API 与 Worker 的职责。前端、业务规格、SQL 和运维资产仍在同一仓库。

```text
backend-go/
├── cmd/personalos/             启动入口与信号退出
├── internal/
│   ├── app/                    组合服务、路由和 Worker 生命周期
│   ├── platform/
│   │   ├── api/                信封、错误码、分页
│   │   ├── config/             环境变量、profile、启动验证
│   │   ├── http/               请求 ID、中间件、上传、SSE、错误处理
│   │   ├── database/           数据源、事务、迁移历史兼容
│   │   ├── auth/               会话、CSRF、锁定、共享会话
│   │   ├── idempotency/        HTTP/工具幂等与执行审计存储
│   │   ├── confirmation/       一次性授权与处理器注册
│   │   ├── cache/              有界本地/Redis 缓存
│   │   └── observability/      业务指标和结构化日志
│   ├── task/                   任务、标签、状态、查询
│   ├── model/                  配置、多模型档案、探测、协议适配
│   ├── context/                预算、摘要、token、窗口保护
│   ├── chat/                   会话、消息、持久化运行与附件
│   ├── agent/                  工具、计划、确认、提问/跟进
│   ├── memory/                 分层、排序、去重、自动沉淀
│   ├── calendar/               重复日程、提醒与投递
│   ├── knowledge/              摄入、索引、检索、RAG、治理
│   ├── mcp/                    客户端与只读对外工具
│   ├── search/                 跨模块全局搜索
```

上图为最终目标，不通过空目录或空接口冒充模块完成。当前仅创建真实使用的基础包。inventory.md 的目标目录是职责分配，不强制逐文件一对一复制。

## 实施原则

- HTTP 层 → 业务服务 → 仓储/事务；DTO 不直接暴露持久化结构。
- 写操作通过业务服务。通过构造参数组合依赖，避免全局服务定位器。
- 事务中只做必要的读/校验/提交；慢模型、解析和网络操作放在事务外。
- 使用 context 传播取消、截止时间、请求 ID 和执行身份，避免将 HTTP 请求取消错误传播到持久化后台运行。
- 所有并发令牌、流、goroutine、客户端连接和租约具有明确生命周期与释放路径。
- Redis、RabbitMQ、OpenSearch、S3 保持可选。数据库任务/幂等/Outbox 仍为事实来源。
- 默认不改现有前端。只有已验收的 Go 模块才允许进入迁移测试代理；禁止在生产数据上按路径混跑 Java/Go 写入。

## 数据迁移路线

1. 首先在隔离 PostgreSQL/pgvector 实例重放原始 42 个 SQL，保存 schema 与约束快照。
2. 明确 Flyway 执行权：过渡期由 Java 或单独迁移步骤执行，Go 启动只校验 schema；不与 Java 争抢迁移锁。
3. 评估 Go 迁移库之前，验证 Flyway checksum/history 的语义；不伪造 `flyway_schema_history`。采用不同历史表也要保证既有版本识别和单执行器互斥。
4. 从 Java 备份恢复第二套数据做读写验收，包含密钥密文、向量与附件。
5. Go 需要追加 schema 时，在复用的 SQL 迁移目录追加版本，不修改历史脚本；更新基线时显式审查。
6. 上线前停止入口写入和全部 Worker，备份并记录待执行任务状态，再切换。发现不兼容时停 Go、核查副作用与数据兼容后恢复 Java；有破坏性变更时不能承诺无损即时回退。

## Java/Go 对照测试

- 两套隔离数据库、附件命名空间、Redis namespace、RabbitMQ vhost 与 OpenSearch index。
- 使用同一组固定时间/随机种子/模拟模型与外部 MCP/Webhook fixtures。
- 相同请求分别打到两个环境，对比 HTTP 状态、业务码、字段缺失/null/空数组、排序、文件与 SSE 事件序列。
- 对 UUID、生成时间、耗时等动态字段按契约归一化；不能把业务日期、排序与 token 预算全部忽略。
- 比较数据库副作用与外部服务调用次数，避免响应一致但重复写入。
- 第三套恢复环境验证崩溃/超时/租约过期/重复投递，以及从实际基线备份恢复。
- 使用现有 frontend/test、scripts/e2e 和 scripts/eval 作为资产，新增 Go 对照入口，不直接废弃原断言。

## Complexity Tracking / 宪法兼容说明

现有宪法绑定 Java/Spring、Java 接口和 Flyway。本分支依据用户明确要求开展 Go 迁移，语言与框架约束在迁移范围内由 Go 等效机制代替；这不授权改变业务边界和安全原则。

约束 | 处理
--- | ---
Java / Spring / Maven | 本分支新增 Go 模块，原 Java 构建保留用于对照；用户明确授权的技术迁移
显式 Java Agent 接口 | 改为显式 Go 工具定义、输入校验和同样的人工确认/审计，不放开模型任意副作用
JPA 与构造器注入 | 仓储/DTO 分离、构造函数依赖组合，保留写路径与事务规则
Flyway | 保留既有迁移与历史；迁移执行器单独决策并验证
单部署/模块化单体 | 保持一个 Go 应用及现有五种运行角色，不新增业务微服务
阶段串行与可验证交付 | P0–P8 依次推进；只报告实际执行过的验证
提交前 Java/前端门禁 | 2026-11-03恢复环境后原Java offline verify通过：1137测试、0失败/错误/跳过，行85.60%/分支69.62%高于原83%/65%阈值；前端类型与生产构建、Go全量race/integration vet/build、真实TLS存储与进程回归通过。未降低原门禁；全量合并/切换仍须P2–P8及五发布门禁

合并替换 main 前更新项目宪法、README 和贡献指南的技术栈说明；不得在尚未完成迁移时提前把仓库描述成 Go 全量实现。
