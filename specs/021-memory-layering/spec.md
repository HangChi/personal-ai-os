# Feature Specification: 阶段 21 — 记忆分层与近重复消解

**Feature Branch**: `021-memory-layering`

**Created**: 2026-10-28

**Status**: Implemented

## 背景：R-03 的结论是对的，但它留下两个缺口

阶段 8 的 research R-03 明确否决了「记忆做向量召回」，理由是记忆是**约束性事实**：

> 向量检索要把「取最近 N 条」换成「取最相似 N 条」，而对话里没提到「周报」时，
> 「周报每周五交」仍然必须生效。相似度检索恰恰会在此时漏掉它。

这个判断今天仍然成立，本阶段**不推翻它**。但 R-03 的落地留下了两个缺口：

1. **没有「必须常在」的表达方式**。R-03 自己也写了「正确方向是分层（常驻 / 按需）」，
   但当时没实现。结果是所有记忆一律平等，预算一紧就只能靠「谁更新」决定谁生效——
   而一条三个月前定下的硬约束，往往正是最该保留的那条。
2. **去重只能识别「一字不差」**。V17 的 `content_hash` 唯一键对「周报每周五下午交」
   与「周报改成每周五下班前交」完全无效，两条语义冲突的约束会同时注入。

## 决策

### D1 分层，而不是召回

新增 `memory.pinned`。常驻条目**无条件注入并优先占预算**，其余仍在预算内全量填充。
注入集合不因相似度变小 —— 这是与「向量召回」的关键区别。

### D2 向量只用于两件事

- **排序微调**：决定预算内**先放谁**，不决定「放不放」；
- **近重复判定**：写入时若与既有条目余弦 ≥ 0.92，旧条目记 `superseded_by`（不物理删除）。

排序降级链：向量余弦 → 字符二元组重叠 → 最近修改优先。任何一环失败都不影响注入。

### D3 常驻意图随内容转移

旧条目被取代时，如果它是常驻的，新条目继承常驻标记。用户置顶的是「这件事」，
不是「这一行记录」——不转移的话，改一次措辞就会让硬约束悄悄失去保护。

### D4 嵌入失败一律降级

记忆的核心价值是「能被记住」，向量只是增强。嵌入端点挂掉、超时、维度不符，
一律返回空并继续保存。查询向量的等待上限 400ms（它在每轮对话的关键路径上）。

## 验收

1. 一条常驻记忆即使很旧、与本轮问题无关，也必须出现在注入块的前部。
2. 记忆数超过预算时，超出部分整条跳过（不截断）。
3. 写入「周报改成每周五下班前交」后，旧条目 `superseded_by` 指向新条目，且不再注入。
4. 关闭 `app.memory.ranking.enabled` 后，行为回到阶段 8（bigram 排序），注入集合不变。
5. 嵌入模型不可用时，保存记忆仍然成功，只是该条暂不参与相关度排序。
6. 存量记忆在启动后由后台任务补向量；补不动时退出，不死循环。

## 数据迁移

`V26__memory_layering_and_dedup.sql`：新增 `pinned` / `superseded_by` / `embedding` /
`embedding_model` / `embedded_at` / `hit_count` / `last_used_at`，以及 HNSW 索引与
「有效条目」部分索引。

## 已知局限

- `hit_count` 只在渲染路径低频率累加（10 分钟间隔）。它用于回答「这条有没有用」，
  不参与衰减计算 —— 衰减用的是 `updated_at`，避免估算路径（仪表盘）污染真实计数。
- 切换 embedding 模型后，旧向量因 `embedding_model` 不一致而不再参与比较，
  需要等回填任务重算。这段时间内该批条目靠 bigram 兜底。
