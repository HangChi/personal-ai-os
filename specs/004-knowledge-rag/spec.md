# Feature Specification: 阶段 3 — 个人知识库与 RAG

**Feature Branch**: `004-knowledge-rag`

**Created**: 2026-10-14

**Status**: Draft

**Input**: 用户需求：「使用 Spring AI 的 DocumentReader、EmbeddingModel、VectorStore 和 pgvector，实现 Markdown/TXT 文件上传、解析、分块、向量化、检索和问答。支持文档删除及向量清理，回答附带引用来源。Embedding 维度与 pgvector 表结构必须一致，并编写至少 5 个可重复执行的 RAG 测试用例。」

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 上传文档并建立索引（Priority: P1）

作为用户，我希望把本地的 Markdown / TXT 笔记上传进来，系统自动解析、切分并建立向量索引，这样我后面就能对自己的资料提问。

**Why this priority**：没有索引就没有检索。这是本阶段全部能力的起点。

**Independent Test**：上传一个 Markdown 文件，随后能看到该文档出现在文档列表中且带有分块数；数据库中该文档的向量条数与分块数一致，且每条向量的维度等于表定义维度。

**Acceptance Scenarios**：

1. **Given** 系统就绪，**When** 上传一个 `.md` 文件，**Then** 返回文档标识、分块数，且文档列表中出现它。
2. **Given** 已上传的文档，**When** 检查向量库，**Then** 该文档的每条向量维度都等于表结构定义的维度。
3. **Given** 不支持的类型（如 `.pdf`）或空文件，**When** 上传，**Then** 返回明确的参数错误，且**不产生任何向量或文档记录**。
4. **Given** 文件超过大小上限，**When** 上传，**Then** 被拒绝并说明上限。

---

### User Story 2 - 基于知识库问答并附引用（Priority: P1）

作为用户，我希望问一个问题后得到基于我资料的回答，并且**能看出答案是从哪段内容来的**，这样我才能判断可不可信。

**Why this priority**：这是知识库的价值出口。没有引用的 RAG 无法验证，用户不会信任。

**Independent Test**：向知识库提问，回答正文与引用列表同时返回；引用指向真实存在的文档与片段。

**Acceptance Scenarios**：

1. **Given** 知识库中有相关文档，**When** 提问，**Then** 返回回答正文 + 引用列表（每条含文档标题、片段序号、片段内容、相似度）。
2. **Given** 知识库中**没有**相关内容，**When** 提问，**Then** 明确说明「知识库中没有找到相关内容」，而不是编造答案。
3. **Given** 提问需要多段内容才能回答，**When** 提问，**Then** 调用模型时携带的上下文包含这些片段，且被标注了编号以便引用。
4. **Given** 未配置模型，**When** 提问，**Then** 返回明确的「AI 未配置」错误（沿用既有错误码）。

---

### User Story 3 - 检索可单独调用（Priority: P2）

作为用户/开发者，我希望检索本身能单独调用（不经模型），这样我能直接看到「检索到了什么」，便于排查「答非所问」。

**Why this priority**：RAG 出问题时，先要分清是**检索**错了还是**生成**错了。单独的检索接口是这条分界线。

**Independent Test**：调用检索接口，返回按相似度排序的片段列表，不触发任何模型生成。

**Acceptance Scenarios**：

1. **Given** 知识库有内容，**When** 用某主题检索，**Then** 返回该主题的片段，且主题相关文档的片段排在前面。
2. **Given** 指定返回条数，**When** 检索，**Then** 返回条数不超过该值。
3. **Given** 检索结果，**When** 查看每条结果，**Then** 能看到来源文档标题与相似度分数。

---

### User Story 4 - 文档删除与向量清理（Priority: P1）

作为用户，我希望删掉文档时它的向量也一并清掉，不留残余，否则后续提问会引用到我已经删除的内容。

**Why this priority**：残留向量会造成「答出已删除内容」这种**极难排查的幽灵行为**。

**Independent Test**：删除文档后，该文档的向量条数为 0，文档列表不再返回它；再次检索也查不到它的内容。

**Acceptance Scenarios**：

1. **Given** 已上传的文档，**When** 删除它，**Then** 文档记录消失，且该文档的向量条数变为 0。
2. **Given** 两个文档内容相近，**When** 删除其中一个，**Then** 另一个的向量**完全不受影响**。
3. **Given** 删除不存在的文档，**When** 调用删除，**Then** 返回「资源不存在」。
4. **Given** 删除后，**When** 用只会命中该文档的关键词检索，**Then** 检索结果为空。

---

### User Story 5 - 在对话中使用知识库（Priority: P2）

作为用户，我希望在对话里直接问我的资料，助手自己去查知识库，而不是让我切到另一个页面。

**Why this priority**：体验统一性；但独立问答接口已能满足核心需求。

**Independent Test**：在对话中提出与知识库相关的问题，助手调用了知识库检索工具，且工具执行日志中有记录。

**Acceptance Scenarios**：

1. **Given** 知识库有内容，**When** 在对话中提问，**Then** 助手调用检索工具并基于结果作答。
2. **Given** 工具被调用，**When** 查看工具执行日志，**Then** 有对应记录且状态为成功。
3. **Given** 知识库为空，**When** 在对话中提问，**Then** 工具返回「没有找到相关内容」，助手据此说明，而不是编造。

---

### Edge Cases

- **维度不一致**：Embedding 模型输出维度与 `vector_store` 表定义不一致时，必须在写入前被拦住并给出可操作的提示，而不是写入一半或抛出原始 SQL 错误。
- **表维度与配置不一致**：启动时必须校验「表里的向量维度 == 配置的维度」，不一致则**启动失败**并说明如何修复。
- **中文/英文混排**：切分不得把 UTF-8 多字节字符截断成乱码。
- **GBK/含 BOM 的文件**：应能识别并给出可读错误或正确解码，而不是写入乱码向量。
- **超长单行**：没有换行的长文本仍必须被切分成多块。
- **重复上传同一文件**：视为两个独立文档（各自可单独删除），不静默去重。
- **超大文件**：超过上限直接拒绝，不进入解析。
- **删除过程中部分失败**：不得出现「文档记录已删但向量还在」或反之；清理顺序必须让失败可恢复。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**：系统 MUST 支持上传 `.md` / `.markdown` / `.txt` 文件并建立索引。
- **FR-002**：系统 MUST 使用 DocumentReader 解析上传内容、使用分块器切分为片段、使用 EmbeddingModel 向量化、写入 VectorStore。
- **FR-003**：每个片段 MUST 携带来源元数据：所属文档标识、文档标题、片段序号。
- **FR-004**：系统 MUST 提供文档列表，含标题、文件名、大小、分块数、上传时间。
- **FR-005**：系统 MUST 提供文档删除，并**同时清理该文档的全部向量**。
- **FR-006**：删除 MUST 保证不残留向量，且不影响其它文档的向量。
- **FR-007**：系统 MUST 提供基于知识库的问答接口，返回回答正文与**引用列表**。
- **FR-008**：引用 MUST 含：文档标识、标题、片段序号、片段内容、相似度。
- **FR-009**：检索结果为空时，问答 MUST 明确告知「未找到相关内容」，MUST NOT 编造回答。
- **FR-010**：系统 MUST 提供独立的检索接口（不触发模型生成）。
- **FR-011**：检索 MUST 支持指定返回条数，并 MUST 有上限。
- **FR-012**：问答与检索 MUST 支持相似度阈值，低于阈值的片段不得进入上下文。
- **FR-013**：系统 MUST 在启动时校验「`vector_store` 表的向量维度 == 配置的嵌入维度」，不一致时启动失败并给出修复指引。
- **FR-014**：写入向量前 MUST 校验嵌入维度与表定义一致；不一致时给出可读错误且**不产生部分写入**。
- **FR-015**：系统 MUST 通过配置切换嵌入模型（与既有聊天模型配置风格一致）。
- **FR-016**：系统 MUST 在未配置嵌入模型时**正常启动**，仅在调用知识库功能时返回明确错误。
- **FR-017**：文件类型、大小、空文件、非法编码 MUST 在边界处校验，失败时零写入。
- **FR-018**：所有新接口 MUST 使用既有统一响应结构。
- **FR-019**：知识库检索 MUST 以 Agent 工具形式提供给对话（复用阶段 2 的工具机制）。
- **FR-020**：所有写操作 MUST 经过 Service 层；MUST NOT 向前端暴露 JPA 实体。
- **FR-021**：数据库结构变更 MUST 由 Flyway 迁移管理；向量表 MUST 由迁移创建（不依赖框架自动建表）。

**范围边界（本阶段明确不含）**：

- 不含 PDF / Word / HTML / 网页抓取等其它格式（仅 Markdown 与 TXT）。
- 不含混合检索与重排序（用户已确认本阶段只做纯向量检索）。
- 不含知识库的「集合/命名空间」划分与多用户隔离。
- 不含原文存储与原文下载（只保留分块后的片段）。
- 不含定时重建索引、增量同步与文档版本管理。
- 不含图片/表格等非文本内容的抽取。
- 不含问答的流式输出（问答为一次性返回结构化结果，便于引用溯源）。

### Key Entities

- **KnowledgeDocument（知识文档）**：标题、原始文件名、内容类型、字节数、字符数、分块数、上传时间。删除它必须连带删除其向量。
- **DocumentChunk（文档片段 / 向量）**：文本内容、来源文档标识与标题、片段序号、向量、相似度（检索时）。
- **Citation（引用）**：问答回答中引用的片段及其来源信息。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：上传一个 Markdown 文件后，`knowledge_document.chunk_count` 与 `vector_store` 中该文档的向量条数**完全相等**。
- **SC-002**：`vector_store` 中**每一条**向量的维度都等于表定义维度（用 SQL 逐行校验，不是抽查）。
- **SC-003**：删除文档后，该文档在 `vector_store` 中的向量条数**为 0**；其它文档的向量条数**不变**。
- **SC-004**：针对某主题提问时，检索返回的**第一条**结果来自该主题对应的文档。
- **SC-005**：问答接口返回的引用列表**非空**且每条的片段内容都能在原文中找到（可逐条断言）。
- **SC-006**：不支持的类型 / 空文件 / 超限文件的请求，`knowledge_document` 与 `vector_store` 的变化行数均为 **0**。
- **SC-007**：维度不一致时，`vector_store` 变化行数为 **0**，且错误信息中包含「维度」二字以便定位。
- **SC-008**：至少 **5 个** RAG 测试用例可在无网络、无 API 密钥的条件下**重复执行**且结果稳定。
- **SC-009**：未配置嵌入模型时应用仍能启动、健康检查返回 200。

## Assumptions

- 仅支持 UTF-8 编码的 `.md` / `.markdown` / `.txt`，单文件上限 **5 MiB**。
- 默认嵌入模型 **bge-m3（1024 维，Ollama）**；维度写进 Flyway 迁移，并做启动期一致性校验（FR-013）。
- 问答为**一次性返回**（非流式）：引用溯源需要结构化的结果，流式与结构化引用在本阶段不可兼得。
- 问答的相似度阈值默认 **0.3**、返回条数默认 **4**，均可配置。
- 「引用」的来源信息取自**检索到的片段元数据**，不由模型生成 —— 模型只负责用 `[n]` 标记引用编号。
- 不保存原文：只保存分块后的片段。若需重新切分，需重新上传。
