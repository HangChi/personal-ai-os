# Requirements Checklist: 阶段 7 — 会话重命名

**Purpose**: 在开始实现前，逐条确认规格「写清楚了、可判定、无内部矛盾」。
**Created**: 2026-10-25 | **Spec**: [spec.md](../spec.md)

## 内容质量

- [x] **无实现细节泄漏**：spec 不提类名、方法名、HTTP 动词（这些在 plan / contracts）。spec 只描述"用户能做什么、系统必须保证什么"
- [x] **用户价值明确**：US-1 的价值是"会话攒到几十条后列表仍可用"，不是"补一个 CRUD 接口"
- [x] **每个故事可独立测试**：US-1 用"改标题后重查列表"可独立验证；US-2 用"三会话改中段"独立验证，不依赖 US-1 之外的任何能力
- [x] **优先级有依据**：US-1 是 P1（本阶段唯一价值来源）；US-2 是 P2，因为它是对 P1 的行为约束而非新能力
- [x] **边界单独列出**：Edge Cases 表覆盖空/空白/超长/恰好 200/带空白/不存在/非法格式/流式中/与自动标题交互
- [x] **「明确不含」有依据**：5 项全部给了理由（宪法原则、阶段串行、成本收益），不是简单罗列

## Requirement 可判定性

| FR | 可判定？ | 判定方式 |
|---|---|---|
| FR-001 只改标题 | ✅ | 改名后断言消息表行数与内容不变 |
| FR-002 去空白 + 空则拒 | ✅ | 输入 `"   x  "` 断言落库 `"x"`；输入 `"   "` 断言 40000 |
| FR-003 长度 200、按归一后算 | ✅ | 200 通过、201 拒绝、`190+40空格` 通过（后者是 R-02 的关键用例） |
| FR-004 不改 updatedAt / 顺序不变 | ✅ | 三会话改中段后 GET 列表顺序断言 |
| FR-005 幂等 | ✅ | 连续两次相同请求，第二次不报错且结果相同 |
| FR-006 不存在 → 404 | ✅ | 合法格式的不存在 id |
| FR-007 非法格式先拒 | ✅ | `../../etc` → 40000，且库状态不变 |
| FR-008 返回完整视图 | ✅ | 响应 `data` 含 `messageCount` 且与改名前一致 |
| FR-009 前端入口 + 同口径校验 | ✅ | store 测试 + 浏览器空值拦截 |

## Success Criteria 可度量性

- [x] SC-001 / SC-003：可用集成测试直接断言数据库行，无"看起来对"空间
- [x] SC-002：用确定的构造数据（三个会话、固定 `updatedAt`）而非时间竞争，断言稳定
- [x] SC-004：type-check + build + store 测试可自动化；点击路径标真机项，不混淆两者

## 与宪法的对齐核对

| 宪法条款 | 本规格如何满足 |
|---|---|
| I. 简单优先 | 零新依赖、零迁移；R-04 明确拒绝为极窄路径加状态列，并登记了"不加的代价" |
| II. 边界即安全 | 改名可逆、不破坏数据，故不加确认；模型侧无改名工具，只有人能发起 |
| III. 分层与写路径收敛 | 写操作在 Service；DTO 对外；校验唯一（R-02 说明为何不在 DTO 加 `@Size`） |
| IV. 数据可追溯 | 无结构变更 ⇒ 无迁移，符合"结构变更才走迁移"的反面要求 |
| V. 可验证的交付 | 每条 SC 都指向具体验证动作；未验证项必须标 ⏳ 并写原因 |
