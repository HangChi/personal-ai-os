# Feature Specification: 阶段 7 — 会话重命名

**Feature Branch**: `007-chat-session-rename`

**Created**: 2026-10-25

**Status**: Draft

**Input**: 用户需求：「按照建议的几个缺口，帮我逐个实现」的第一项 —— 会话目前只能删除、不能改名。

## 背景

阶段 1 实现了会话的创建、列表、消息查询与删除，标题有两条来源：

1. 创建时由用户指定，缺省为「新会话」；
2. 首条用户消息写入前，用消息前 30 字自动生成（仅当标题仍是「新会话」且会话无消息）。

两条来源都没有覆盖一个真实场景：**会话攒多了以后，自动生成的 30 字标题不足以为我所用**。
用户能看到标题、能删掉整个会话，却无法把它改成「报销流程问答」这样的名字。这是阶段 1 的显式遗留缺口。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 给已有会话改名（Priority: P1）

作为用户，我希望把某个会话的标题改成我自己能认出来的描述，这样会话列表在积累几十条之后仍然可用。

**Why this priority**：这是本阶段的全部价值。没有它，本阶段没有存在的理由。

**Independent Test**：选一个已有会话，把标题改成新值，重新拉取会话列表，该会话的标题为新值且其余字段不变。

**Acceptance Scenarios**：

1. **Given** 存在一个会话，**When** 提交新的标题，**Then** 返回该会话的最新视图，标题为**去除首尾空白后**的新值。
2. **Given** 已经改过一次标题，**When** 再次改成同一个值，**Then** 结果与第一次相同（幂等，不报错）。
3. **Given** 该会话已有若干轮消息，**When** 改名，**Then** 消息记录一条都不受影响。

---

### User Story 2 - 改名不干扰会话排序（Priority: P2）

作为用户，我希望改个名字不要让会话「跳到列表最前面」，这样我正在按时间翻找的上下文不会被打断。

**Why this priority**：这是对 P1 的行为约束而非独立价值。但它决定了一个容易被实现错的点：
列表按「最近活动时间」倒序，如果把改名算作活动，用户每次改名都会丢失自己在列表里的位置。

**Independent Test**：给列表中段的一个会话改名，重新拉取列表，该会话仍在原来的相对位置。

**Acceptance Scenarios**：

1. **Given** 三个会话按 A、B、C 顺序排列（A 最近），**When** 给 C 改名，**Then** 列表顺序仍为 A、B、C。
2. **Given** 一个会话被改名，**When** 查询该会话，**Then** 「最近活动时间」保持改名前的值。

---

### Edge Cases

| 输入 | 期望行为 |
|---|---|
| 标题为空串 / 全空白 | 拒绝，`40000 参数校验失败`，文案「标题不能为空」 |
| 标题超过 200 字符（**去除首尾空白后**计算） | 拒绝，`40000`，文案「标题长度不能超过 200」 |
| 标题恰好 200 字符 | 接受 |
| 标题首尾带空白 | 接受，落库前去除 |
| 会话不存在 | `40004 资源不存在` |
| 会话标识含非法字符（如 `../`、空格、超 64 位） | `40000`，文案「会话标识格式非法」，**在查库之前**就拒绝 |
| 会话正在流式生成中 | 允许改名（标题与服务端流式互不影响） |
| 会话无消息且标题被改成「新会话」字面量 | 接受；若随后写入首条消息，标题会被自动标题覆盖（见 Assumptions） |

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**：系统 MUST 提供修改单个会话标题的能力，且只修改标题，不触碰消息。
- **FR-002**：标题 MUST 在落库前去除首尾空白；去除后为空则 MUST 拒绝。
- **FR-003**：标题长度上限 MUST 为 200，按**去除首尾空白后**的字符数计算，与创建会话时同一上限。
- **FR-004**：改名 MUST NOT 更新会话的「最近活动时间」，因此会话在列表中的相对位置 MUST 保持不变。
- **FR-005**：改名 MUST 幂等 —— 连续两次提交相同标题，第二次 MUST NOT 报错，结果相同。
- **FR-006**：会话不存在时 MUST 返回「资源不存在」，MUST NOT 静默创建新会话。
- **FR-007**：会话标识格式非法时 MUST 在访问数据库前拒绝（沿用阶段 1 的格式规则 `[A-Za-z0-9-]{1,64}`）。
- **FR-008**：接口 MUST 返回更新后的会话完整视图（含消息条数），使前端无需二次请求即可刷新单条记录。
- **FR-009**：前端 MUST 在会话列表中提供改名入口，且 MUST 预填当前标题、MUST 在提交前做与后端同口径的非空与长度校验。

### Key Entities

- **ChatSession（已存在，不新增字段）**：`conversationId`、`title`、`createdAt`、`updatedAt`、`messageCount`（派生）。本阶段只写 `title`。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：改名成功后，重新拉取会话列表，100% 的会话标题为用户提交的值（去空白后）。
- **SC-002**：改名后会话在列表中的相对顺序 100% 不变（以 3 个以上会话、改中段会话为验证场景）。
- **SC-003**：空标题、全空白、201 字符、非法会话标识四种输入，全部返回 400 类错误且数据库无任何写入。
- **SC-004**：前端会话列表提供可见的改名入口，改名后无需刷新页面即可看到新标题。

## Assumptions

- **不新增数据库列**。是否「被用户显式改过名」不单独记状态；自动标题的既有条件（标题等于默认文案且会话无消息）保持不变。
  代价：若用户把一个**尚无消息**的会话改名成字面量「新会话」，随后发首条消息，标题会被自动标题覆盖。
  该路径需要「空会话 + 恰好取名默认文案」两个条件同时成立，为它增加一个状态列（含迁移、实体字段、额外分支）
  的收益不足 —— 宪法原则 I「任何新增抽象层 MUST 能回答不这样做的具体代价是什么」，这里的代价就是这一条极窄的边界行为。
- **不改 `updatedAt`**：该字段语义是「最近一次对话活动」，改名不是对话活动（FR-004）。
- **不做二次确认**：改名可逆、无数据破坏风险，不属于必须人工确认的操作（与删除会话区别对待）。
- 本地单用户，无权限与多租户概念。

## 明确不含（Explicitly Out of Scope）

| 不做的事 | 依据 |
|---|---|
| 批量改名 | 无对应使用场景；批量操作需确认机制，成本与收益不匹配 |
| 由模型自动重命名会话 | 与「显式」原则冲突，且模型改写标题不可预期 |
| 会话搜索、置顶、归档、分组 | 属独立特性，不应夹带进本阶段（宪法：阶段严格串行） |
| 标题唯一性约束 | 允许多个会话同名是合理需求（如两个不同项目的「周报」） |
| 历史标题 / 改名审计 | 单用户在本地使用，无人需要追溯谁改了名 |
