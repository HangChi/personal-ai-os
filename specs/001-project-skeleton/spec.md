# Feature Specification: 阶段 0 — 项目骨架初始化

**Feature Branch**: `001-project-skeleton`

**Created**: 2026-10-14

**Status**: Draft

**Input**: 用户需求：「Personal AI OS 是一个开源、自托管、可扩展的个人智能操作系统……请帮我初始化整个项目骨架。严格按阶段完成，不要一次生成整个系统。当前只完成阶段 0。」

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一键拉起本地基础设施 (Priority: P1)

作为开发者，我希望用一条命令启动项目所需的数据库基础设施（含向量检索能力），这样我不必手工安装和配置数据库，就能开始开发。

**Why this priority**：数据库是后续所有模块（对话记忆、任务、知识库、日程）的共同前置。没有它，任何业务模块都无法落地，属于典型的「阻塞性基础能力」。

**Independent Test**：在干净环境执行一条启动命令后，能用官方客户端连上数据库并成功执行一条查询；再次执行停止命令后，数据卷保留、端口释放。

**Acceptance Scenarios**：

1. **Given** 本机已安装容器运行时且未占用目标端口，**When** 执行启动命令，**Then** 数据库服务在 30 秒内变为健康状态，且对外暴露的连接参数与项目模板中的默认值一致。
2. **Given** 数据库服务已启动，**When** 使用模板中的默认凭据连接，**Then** 能成功建立连接并执行 `SELECT 1`。
3. **Given** 数据库服务已停止，**When** 重新启动，**Then** 之前写入的数据仍然存在（数据卷持久化）。

---

### User Story 2 - 后端骨架可构建、可启动、可自查 (Priority: P1)

作为开发者，我希望后端工程能够一次构建通过、正常启动，并提供一个健康检查入口，这样我能确认「工程是活的」，并把它作为后续所有业务模块的挂载点。

**Why this priority**：后端是整个系统的承载主体。一个不可构建或不可启动的骨架，会让后续每个阶段的验证都失去基准。

**Independent Test**：在干净检出上执行后端构建与测试命令，全部通过；启动应用后访问健康检查入口，返回成功结构。

**Acceptance Scenarios**：

1. **Given** 一份干净检出的代码和可用的构建工具链，**When** 执行后端构建与测试命令，**Then** 命令成功退出且测试全部通过。
2. **Given** 数据库可用且应用已启动，**When** 访问健康检查入口，**Then** 返回 HTTP 200 与统一响应结构（成功码 + 状态数据）。
3. **Given** 应用已启动，**When** 请求一个不存在的路径，**Then** 返回统一的错误响应结构，且不包含堆栈或内部类名。
4. **Given** 请求体不满足校验规则，**When** 调用任一已实现接口，**Then** 返回统一的参数错误响应，并指出字段问题。

---

### User Story 3 - 前端骨架可构建、可启动、可连后端 (Priority: P2)

作为开发者，我希望前端工程能够一次构建通过、正常启动，并在页面上真实调用后端健康检查接口，这样我能确认前后端链路已经打通。

**Why this priority**：前端是用户与系统交互的唯一入口。链路打通后，后续每个业务模块都能直接接入界面。

**Independent Test**：在干净检出上执行前端依赖安装与生产构建，构建成功；启动开发服务后打开首页，页面展示后端返回的健康状态。

**Acceptance Scenarios**：

1. **Given** 干净检出，**When** 执行前端依赖安装与生产构建，**Then** 构建成功并产出可部署的静态产物。
2. **Given** 后端已启动且前端开发服务已启动，**When** 打开首页，**Then** 页面显示后端健康状态，且不出现跨域错误。
3. **Given** 后端未启动，**When** 打开首页，**Then** 页面给出可读的失败提示，而不是白屏或未捕获异常。

---

### User Story 4 - 新贡献者可按文档跑起来 (Priority: P3)

作为外部贡献者，我希望 README 与文档能让我在不问任何人的情况下把项目跑起来，这样我才能评估并参与这个开源项目。

**Why this priority**：项目以开源为目标，可复现的上手路径是外部贡献的前提；但它不阻塞内部开发，故优先级低于前三者。

**Independent Test**：仅阅读仓库内文档，在一台干净机器上完成「启动基础设施 → 启动后端 → 启动前端」全流程。

**Acceptance Scenarios**：

1. **Given** 一个新克隆的仓库，**When** 仅按 README 步骤操作，**Then** 能依次启动基础设施、后端与前端，且每一步都有可观察的成功标志。
2. **Given** 仓库已完成提交，**When** 检查仓库内容，**Then** 不含任何真实密钥，且包含明确的开源许可证。

---

### Edge Cases

- **端口被占用**：目标数据库端口已被其它服务占用时，应能通过配置项改用其它端口，且文档说明如何改。
- **凭据未提供**：未设置环境变量时，应使用文档中标注的本地默认值，保证开箱可跑；但默认值 MUST 仅用于本地。
- **数据库未启动时启动后端**：应用应明确失败并给出可读原因，而不是静默启动后每次请求才报错。
- **数据库迁移重复执行**：同一迁移在已迁移过的库上重复运行，应被识别为「无需变更」而非报错。
- **健康检查依赖不可用**：数据库不可用时，健康检查应反映「不健康」，而不是把异常抛成 500 堆栈。
- **前端后端不同源**：开发期前端与后端不同端口，必须通过开发服务器代理转发，避免跨域。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**：仓库 MUST 采用单仓库（Monorepo）结构，至少包含后端应用、前端应用、文档与本地基础设施编排文件四类内容。
- **FR-002**：仓库 MUST 提供一条命令启动本地数据库基础设施，并 MUST 使用支持向量检索的数据存储镜像。
- **FR-003**：基础设施编排 MUST 支持通过环境变量覆盖数据库名、用户名、密码与端口。
- **FR-004**：仓库 MUST 提供环境变量模板文件，列出所有必需变量及其本地默认值；该模板 MUST NOT 含真实密钥。
- **FR-005**：后端 MUST 使用 Java 21 与 Spring Boot 4.1.x 构建，并 MUST 通过一个权威的依赖清单统一管理 AI 相关依赖版本。
- **FR-006**：后端 MUST 提供唯一的启动入口类，且应用名 MUST 为 `personal-ai-os`。
- **FR-007**：后端 MUST 按业务模块划分包结构，至少覆盖：公共、AI、智能体、对话、任务、知识库、日程、记忆八个模块。
- **FR-008**：后端 MUST 提供统一的成功/失败响应结构：包含业务码、提示信息、数据体与时间戳。
- **FR-009**：后端 MUST 提供全局异常处理，至少覆盖：业务异常、参数校验失败、资源不存在、未捕获异常；且 MUST NOT 向调用方泄漏堆栈。
- **FR-010**：后端 MUST 提供健康检查入口，返回应用状态与版本信息，并使用统一响应结构。
- **FR-011**：后端 MUST 提供参数校验能力，且校验失败时返回统一错误响应。
- **FR-012**：所有数据库结构变更 MUST 由版本化迁移脚本管理；首版迁移 MUST 建立向量检索与唯一标识所需的基础扩展。
- **FR-013**：后端 MUST NOT 使用 ORM 自动建表能力修改结构（仅允许校验模式）。
- **FR-014**：数据库连接、应用端口等配置 MUST 来自配置文件并可由环境变量覆盖。
- **FR-015**：后端 MUST 使用构造器注入；MUST NOT 使用字段注入。
- **FR-016**：前端 MUST 使用 Vue 3 + TypeScript + Vite 构建，并 MUST 集成路由、状态管理与 UI 组件库。
- **FR-017**：前端 MUST 提供统一的后端调用客户端，并 MUST 在开发期通过代理规避跨域。
- **FR-018**：前端首页 MUST 真实调用后端健康检查接口并展示结果，失败时给出可读提示。
- **FR-019**：仓库 MUST 提供 `.gitignore`，忽略构建产物、依赖目录、本地环境文件与本地工作区数据。
- **FR-020**：仓库 MUST 提供中文 README，包含：项目定位、技术栈、目录结构、启动步骤与阶段路线图。
- **FR-021**：仓库 MUST 包含明确的开源许可证文件。
- **FR-022**：项目 MUST 以 Spec Kit 流程管理：宪法、特性规格、实现计划与任务清单齐备。
- **FR-023**：仓库 MUST 提供后端单元测试与集成测试，且 MUST 能在本地一次跑通。

**范围边界（本阶段明确不含）**：

- 不含 AI 模型调用、对话、工具调用与聊天记忆（阶段 1 起）。
- 不含任务、知识库、日程、提醒的任何业务实体与接口（阶段 2–4）。
- 不含向量表的业务建表与检索逻辑（阶段 3）。
- 不含身份认证、多用户、权限、计费与对外部署（第一版为本地单用户）。
- 不含 MCP 集成与 Coding/资讯等独立 Agent 模块。

### Key Entities *(include if feature involves data)*

- **本阶段无业务实体**。阶段 0 只建立数据库基线：启用向量检索扩展、键值扩展与 UUID 生成扩展，为阶段 3 的向量表做准备。
- 后续阶段的实体（任务、对话、消息、知识文档、日程、提醒）在各自阶段的数据模型中定义，本阶段不预建表。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：在干净检出的仓库上，从零到「基础设施 + 后端 + 前端」三者全部就绪，按 README 操作的总耗时不超过 15 分钟。
- **SC-002**：后端构建与测试命令一次通过，且测试包含至少 1 个跨层集成测试（真实数据库）与至少 2 个单元测试。
- **SC-003**：前端在干净检出上执行依赖安装与生产构建一次通过，无类型错误。
- **SC-004**：健康检查入口在数据库可用时 100% 返回成功结构；数据库不可用时返回明确的失败状态而非未处理异常。
- **SC-005**：仓库首次提交中，密钥扫描结果为零命中；`.env` 等敏感文件处于被忽略状态。
- **SC-006**：模块包结构 100% 覆盖 FR-007 列出的八个模块。
- **SC-007**：所有错误响应均为统一结构，且响应体中不出现 Java 类名、堆栈或 SQL 片段。

## Assumptions

- 开发者本机已具备：JDK 21、Docker（或兼容容器运行时）、Node.js 20.19+ 与 npm。未预装 Maven 时使用仓库自带的 Maven Wrapper。
- 本地默认数据库端口若被占用，开发者愿意按文档改用其它端口；默认值仅为本地便利，不用于任何共享环境。
- 阶段 0 不引入任何需要外部密钥的服务，因此骨架在无网络密钥的情况下也能完整启动。
- 前端 UI 组件库在阶段 0 采用全量引入以降低构建配置风险；按需引入作为阶段 1 的优化项，不属本阶段验收范围。
- 「健康」在阶段 0 定义为：应用进程存活 + 能读取到自身版本信息；数据库连通性由框架自带健康端点一并反映。
