# 实施方案

1. 新建共享 ChatSources，来源按文档或安全网页地址分组，使用已有 Element Plus 抽屉；统一在流式与持久化回复下方展示，检索过程放入抽屉内折叠区。
2. 检索结果按消息绑定，完成时转移，恢复时从最新执行记录的最后一次 reset 之后重建，并核对该轮用户及助手文本，防止串轮。不引入持久化字段或数据库迁移。
3. 知识增强先通过现有结构化模型网关结合最近 6 条、每条至多 600 字符的历史判断是否检索并补全问题。路由最多 4 秒，计入检索总预算；无工具、严格 JSON 验证，不以关键词过滤代替语义判断。日程操作不走资料保护短路，资料问题继续受证据保护。独立知识问答不走此路由。
4. Java KnowledgeSearchPort 默认方法和 Go 可选 callback 兼容旧检索桩与配置；上下文读取/路由失败复用原检索降级路径，取消和发布错误继续上传。
5. 组件、状态恢复、路由及多轮集成测试；隔离本机 API mock 浏览器检查移动端、深浅色和生成/完成状态；运行前后端质量门禁。
6. 分开提交实现及迁移登记；同步已有 scope 文件哈希及新增来源组，不改变冻结清单、SQL、5 项发布门禁和候选状态。

## 复杂度与依赖

无新增运行时依赖。共享来源组件避免重复渲染/编号漂移；对话专用检索入口避免改变独立资料问答含义。历史只用于路由理解，原会话记忆和工具授权规则保持原路径。
