# Feature Specification: 阶段 22 — Agent 规划编排

**Feature Branch**: `022-agent-planning`

**Created**: 2026-10-28

**Status**: Implemented

## 背景：只有「边想边做」，没有计划

阶段 2 起，Agent 的能力全靠 Spring AI 的工具循环：模型自己决定调哪个工具，
结果回填后继续，直到不再请求工具。这是 ReAct 式执行，在两三步的任务上很好用，
但任务一长就暴露三个问题：

1. **忘了还剩几步**：上下文窗口只带最近若干条消息，工具结果一大就被裁剪，
   计划一旦滑出窗口，模型是真忘，不是「装作忘了」。
2. **失败后反复重试同一条路**：没有「这一步已经失败」的外部记录，
   模型倾向于换个参数再试一次，而不是换方案。
3. **用户看不到进度**：一轮对话里调了五次工具，用户只看到最后一段回答。

## 决策

### D1 计划落表，而不是留在提示词里

`agent_plan` + `agent_plan_step`。计划成为**可读、可查、可断点续**的外部状态：
模型能通过 `getPlan` 自查（上下文被裁剪后的兜底），前端能渲染进度。

### D2 工具结果由执行外壳回填，不由模型自报

`ToolExecutor` 在每次工具成功后通过 `ToolCallRecorder` SPI 把
「工具名 + 结果摘要」写到当前 RUNNING 步骤上。理由是模型的自述不可靠：
它可能漏报、错报工具名，甚至什么都没调就声称调了。计划面板的全部价值是
「实际发生了什么」。

### D3 一会话至多一个 ACTIVE 计划

部分唯一索引 `uk_agent_plan_active_per_conversation` 保证。新建计划前必须先把旧的
置 `ABORTED` 并 `flush` —— 与「模型配置至多一行 active」是同一个坑：
JPA 不保证先发 UPDATE 后发 INSERT，中间态会撞索引。

### D4 失败不自动重规划

工具失败时系统只把当前步骤标 `FAILED` 并给模型两个选项（`startPlanStep` 重试 /
`revisePlan` 换路线）。重规划意味着前面的部分工作白做，这个决策应该由模型
结合失败原因做，而不是系统替它决定。

### D5 重规划产生新计划，旧计划保留为 ABORTED

就地改步骤会抹掉「原来打算怎么做、走到哪一步、为什么换路」这条线索。

### D6 工具循环有硬上限

`spring.ai.tools.limits`：单工具每轮 6 次、合计 24 次，超限行为
`return_error_response`（**不是**默认的 `throw`——那会打断整条 SSE 流，
用户看到「回答到一半断了」）。

## 状态机

```
PENDING ──start──▶ RUNNING ──complete──▶ DONE
   │                 │
   │                 └──fail──▶ FAILED ──start──▶ RUNNING（允许重试）
   └──skip──▶ SKIPPED
```

- DONE / SKIPPED 是终态，不可再转移；
- 全部步骤到终态 ⇒ 计划自动 `COMPLETED`（否则永远显示「进行中」）。

## 验收

1. 模型对多步任务先 `createPlan` 再执行；单步任务不建计划（工具描述里已约束）。
2. 每步执行期间的工具调用出现在该步的 `toolName` / `toolResult` 上。
3. 某步工具被拒后，该步变 `FAILED`，且工具返回里带有「重试 / 重规划」的提示。
4. 全部步骤完成后计划为 `COMPLETED`；重规划后旧计划为 `ABORTED`。
5. 前端在会话顶部显示计划与进度；无计划时不渲染；计划结束后仍可查看。
6. 工具循环超过上限时，模型收到「已超限」的工具结果并能收尾，而不是流被中断。

## 数据迁移

`V27__create_agent_plan.sql`：两张表、状态 CHECK、部分唯一索引、RUNNING 步骤部分索引。

## 已知局限

- 计划是「一层」的：没有子计划/嵌套。12 步上限是刻意的——超过就不是计划，是愿望清单。
- 步骤与工具的绑定是**隐式**的（按「当前 RUNNING 步骤」归集）。同一时刻只允许一个
  RUNNING 步骤；并发步骤需要显式传 stepId，本阶段不做。
- 前端的计划刷新发生在「一轮结束」与「切换会话」两个时刻，不轮询。
