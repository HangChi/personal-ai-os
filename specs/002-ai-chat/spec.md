# Feature Specification: 阶段 1 — AI 对话与聊天历史

**Feature Branch**: `002-ai-chat`

**Created**: 2026-10-14

**Status**: Draft

**Input**: 用户需求：「使用 Spring AI ChatClient 实现聊天功能，包括多轮上下文、PostgreSQL 聊天历史持久化和 SSE 流式输出。实现会话列表、消息查询及流式聊天 API。保证 conversationId 隔离，支持模型配置和错误处理。」

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 流式对话（Priority: P1）

作为用户，我希望把问题发给助手后**逐字看到回复**，而不是等整段生成完才显示，这样长回答的等待感会显著降低。

**Why this priority**：这是本阶段的全部价值所在。没有流式输出，其余能力都只是数据管道。

**Independent Test**：对某会话发起一次流式请求，能在响应结束前就陆续收到多个内容片段，且最终收到一个表示完成的终止事件。

**Acceptance Scenarios**：

1. **Given** 已存在一个会话，**When** 发起流式对话请求，**Then** 依次收到：开始事件（含 conversationId）→ 多个内容增量事件 → 完成事件（含完整回复）。
2. **Given** 模型侧发生错误，**When** 发起流式请求，**Then** 收到错误事件（含明确错误码与可读文案），而不是连接静默断开。
3. **Given** 请求内容为空或超长，**When** 发起流式请求，**Then** 在建立流之前就返回参数校验失败。

---

### User Story 2 - 多轮上下文（Priority: P1）

作为用户，我希望助手记得本次会话里前面说过的话，这样我不必每轮重复背景。

**Why this priority**：没有上下文，助手等同于一次性问答工具，无法承担「个人助手」定位。

**Independent Test**：在同一会话内连续提问两轮，第二轮的问题中包含只有第一轮才出现过的信息；检查发送给模型的上下文确实包含第一轮的内容。

**Acceptance Scenarios**：

1. **Given** 会话内已有若干轮对话，**When** 发起新一轮提问，**Then** 发送给模型的上下文中包含此前的用户与助手消息，且顺序为时间正序。
2. **Given** 会话历史很长，**When** 发起新一轮提问，**Then** 送给模型的上下文被限制在配置的最大条数内，不会无界增长。
3. **Given** 已经发送过 N 轮，**When** 查询该会话消息，**Then** 能取回**全部**历史消息（不受上下文窗口上限影响）。

---

### User Story 3 - 会话与历史管理（Priority: P2）

作为用户，我希望看到自己的会话列表，并能打开某个会话查看完整聊天记录，这样我能在多次使用之间来回切换。

**Why this priority**：持久化的价值必须通过「可查阅」体现；但即便没有列表页，流式对话本身已可用。

**Independent Test**：新建会话后能在列表中看到它；发送若干消息后能按时间正序查回全部消息。

**Acceptance Scenarios**：

1. **Given** 尚无任何会话，**When** 查询会话列表，**Then** 返回空列表而非报错。
2. **Given** 已创建会话，**When** 查询会话列表，**Then** 该会话出现，且按最近活动时间倒序排列。
3. **Given** 某个会话已有多轮消息，**When** 查询该会话消息，**Then** 按发生顺序正序返回，且每条消息标注角色（用户/助手/系统）。
4. **Given** 存在会话，**When** 删除该会话，**Then** 该会话及其全部消息一并消失，列表与消息查询均不再返回它。
5. **Given** 指定一个不存在的会话标识，**When** 发起流式对话或查询消息，**Then** 返回明确的「资源不存在」，而不是静默创建或返回空。

---

### User Story 4 - 会话隔离（Priority: P1）

作为用户，我希望不同会话之间完全互不串味，这样我可以分别讨论互不相关的主题。

**Why this priority**：隔离一旦失守就是**数据串台**，属于正确性缺陷而非体验问题。

**Independent Test**：在会话 A 中写入只有 A 才有的信息，然后在会话 B 中提问；检查发送给 B 的上下文**不含** A 的任何内容。

**Acceptance Scenarios**：

1. **Given** 会话 A 与 B 均有历史消息，**When** 在 B 中提问，**Then** 送给模型的上下文只含 B 的消息。
2. **Given** 两个会话，**When** 查询各自消息，**Then** 各自只返回自己的消息。
3. **Given** 删除会话 A，**When** 查询会话 B，**Then** B 不受任何影响。

---

### User Story 5 - 模型可配置与可降级 (Priority: P2)

作为自托管用户，我希望通过配置切换模型提供商（本地或云端），并且在模型不可用时得到**可读的失败提示**，而不是白屏或 500 堆栈。

**Why this priority**：自托管项目必须允许用户自带模型；但它是可用性增强，不阻塞核心链路。

**Independent Test**：不配置任何密钥时应用仍能正常启动且健康检查通过；把提供商指向不可达地址时，对话请求返回明确的「AI 服务不可用」错误。

**Acceptance Scenarios**：

1. **Given** 未配置任何模型密钥，**When** 启动应用，**Then** 应用正常启动，健康检查与错误响应仍可用。
2. **Given** 通过配置切换提供商（本地 / OpenAI 兼容），**When** 重启应用，**Then** 无需改动任何代码即可生效。
3. **Given** 模型服务不可达，**When** 发起对话，**Then** 返回「AI 服务调用失败」类错误（可读文案），且响应体不含堆栈。
4. **Given** 模型能力被完全关闭，**When** 发起对话，**Then** 返回明确的「AI 未配置」错误，而不是空指针或 500。

---

### Edge Cases

- **并发写入同一会话**：同一会话被并发请求时，消息顺序号不得冲突；冲突时应重试或拒绝，而不是写入重复序号。
- **历史超长**：历史消息数远超上下文窗口时，取最近 N 条而非全量，且不得因此删除库中历史。
- **生成中途客户端断开**：客户端断连后服务端应停止推送并释放资源，不得写入半截助手消息。
- **空回复**：模型返回空内容时，仍应产生完成事件，且不应写入空消息或写入后应可识别。
- **会话标识非法**：传入超长或含非法字符的标识时，应在校验层拒绝。
- **重复标题**：多个会话标题相同时必须能区分（以标识为准）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**：系统 MUST 提供「创建会话」接口，返回唯一会话标识与标题。
- **FR-002**：系统 MUST 提供「会话列表」接口，按最近活动时间倒序返回。
- **FR-003**：系统 MUST 提供「会话消息查询」接口，按发生顺序正序返回，并标注角色。
- **FR-004**：系统 MUST 提供「流式对话」接口，以 SSE 逐段推送回复内容。
- **FR-005**：流式响应 MUST 包含开始事件、若干增量事件、完成事件；出错时必须推送错误事件而非静默断开。
- **FR-006**：系统 MUST 提供「删除会话」接口，级联删除其全部消息。
- **FR-007**：系统 MUST 持久化用户的每条消息与助手的每条回复，且**库中历史不得被上下文窗口裁剪**。
- **FR-008**：发送给模型的上下文 MUST 仅包含同一会话的消息，MUST NOT 混入其它会话内容。
- **FR-009**：发送给模型的上下文 MUST 按时间正序，且条数受配置上限约束。
- **FR-010**：系统 MUST 通过配置切换模型提供商，MUST NOT 需要改动代码。
- **FR-011**：系统 MUST 在未配置任何模型凭据时正常启动（健康检查可用）。
- **FR-012**：模型调用失败时 MUST 返回可读错误，MUST NOT 泄漏堆栈、类名或上游原始报文。
- **FR-013**：模型能力未启用时，对话接口 MUST 返回明确的「未配置」错误。
- **FR-014**：所有接口 MUST 使用既有统一响应结构；错误码遵守既有契约。
- **FR-015**：所有入参 MUST 在边界校验（非空、长度上限、标识格式）。
- **FR-016**：会话不存在时 MUST 返回「资源不存在」，MUST NOT 静默创建。
- **FR-017**：新建会话的标题 MUST 可由请求指定；未指定时 SHOULD 依据首条用户消息生成。
- **FR-018**：消息顺序 MUST 稳定，MUST NOT 依赖时间戳排序。
- **FR-019**：会话的最近活动时间 MUST 随新消息更新。

**范围边界（本阶段明确不含）**：

- 不含工具调用（Tool Calling）与 Agent 编排（阶段 2）。
- 不含知识库与 RAG 检索（阶段 3）。
- 不含日程与提醒（阶段 4）。
- 不含 MCP 集成。
- 不含多模态输入（图片/语音）与文件上传。
- 不含身份认证与多用户；本阶段仍为本地单用户。
- 不含消息编辑、重新生成、分支对话与点赞反馈。

### Key Entities

- **ChatSession（会话）**：对外标识（即模型上下文标识）、标题、创建时间、最近活动时间。与消息是一对多。
- **ChatMessage（消息）**：所属会话、角色（用户/助手/系统/工具）、文本内容、会话内顺序号、创建时间。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：流式对话的首个内容片段在模型开始返回后 1 秒内推送到客户端（本地模型/桩模型下可稳定复现）。
- **SC-002**：一轮流式对话产生的库记录数恰好为 2（1 条用户 + 1 条助手），且助手的完整文本与增量拼接结果一致。
- **SC-003**：会话隔离测试中，跨会话上下文泄漏数为 **0**。
- **SC-004**：连续 5 轮对话后，库中历史消息数为 10，且送给模型的上下文条数不超过配置上限。
- **SC-005**：未配置任何模型凭据时，应用启动成功、`/api/v1/health` 返回 200。
- **SC-006**：模型不可达时，流式接口在 10 秒内推送错误事件；非流式路径返回统一错误结构且响应体不含堆栈。
- **SC-007**：所有新增接口的参数校验失败率为可观测的 100%（非法输入不进入业务逻辑）。
- **SC-008**：新增集成测试在无外部网络、无 API 密钥的条件下全部通过（使用桩模型）。

## Assumptions

- 阶段 1 仍为**本地单用户**，因此会话不绑定用户维度；`conversationId` 即隔离边界。
- 默认提供商取**本地 Ollama**（无需密钥，符合「开箱可跑」），用户可通过配置切到 OpenAI 兼容的云端服务。
- 「最大上下文条数」默认 20，可按配置调整；该上限**只影响送给模型的内容**，不影响库中历史。
- 客户端采用 `fetch` + 流读取解析 SSE（因对话需要 POST 提交内容，浏览器原生 `EventSource` 不支持带请求体的 POST）。
- 助手回复当前为纯文本，不含结构化输出与引用来源。
