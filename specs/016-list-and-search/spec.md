# Feature Specification: 阶段 16 — 列表分页与站内搜索

**Feature Branch**: `016-list-and-search`

**Created**: 2026-10-25

**Status**: Draft

**Input**: 用户需求：「继续」—— 剩余项中的「知识库列表分页」与「会话搜索」。

## 背景

两个列表接口是「全量返回、无筛选」：

| 模块 | 现状 | 数据会怎么长 |
|---|---|---|
| 知识库 | `GET /api/v1/knowledge/documents` 返回 `List<KnowledgeDocumentDto>` | 文档数随时间单调增长 |
| 对话 | `GET /api/v1/chat/sessions` 返回 `List<ChatSessionDto>` | 会话数随时间单调增长 |

它们都是**只增不减**的列表，目前靠前端一次性渲染。数量少时无感，
但一旦上百条，页面会明显变慢，而且没有关键词搜索，找一条历史会话只能往下翻。

任务模块在阶段 2 就已经解决了这个问题（`page` + `size` + `PageDto` + 关键词筛选），
本阶段把同一套模式补到这两个模块。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 知识库分页与搜索（Priority: P1）

作为用户，我在知识库页翻页查看文档，并能按标题或文件名搜索。

**Why this priority**：知识库是这两个模块里增长更快的（每次上传都是一条）。

**Independent Test**：造 25 个文档，第 1 页只有 20 条且 `total=25`；
搜索一个不存在的词 → `total=0`；搜索一个存在的词 → 只返回匹配项。

**Acceptance Scenarios**：

1. **Given** 文档数超过一页，**When** 打开知识库页，**Then** 显示第 1 页（默认 20 条）
   与总数，能翻页。
2. **Given** 输入标题里的一个词，**When** 搜索，**Then** 只返回标题匹配的文档。
3. **Given** 输入文件名里的词（标题不同），**When** 搜索，**Then** 也能命中。
4. **Given** 搜索无结果，**When** 查看列表，**Then** 显示空态（不是 404 或错误）。

---

### User Story 2 - 会话搜索与分页（Priority: P1）

作为用户，我在对话页按标题找历史会话，会话多了也能翻页。

**Why this priority**：会话列表是对话页的主入口，找不到旧会话会让人重新提问，
而重新提问会产生重复会话。

**Independent Test**：造 25 个会话，分页正常；搜索标题关键词只返回匹配会话。

**Acceptance Scenarios**：

1. **Given** 会话超过一页，**When** 打开对话页，**Then** 分页显示，翻页不重复不遗漏。
2. **Given** 输入标题关键词，**When** 搜索，**Then** 只返回匹配的会话。
3. **Given** 清空搜索词，**When** 回车或点清空，**Then** 回到全部会话且页码归零。
4. **Given** 会话条目显示的消息条数，**When** 翻页，**Then** 每行的消息条数仍然正确。

## Edge Cases

| 输入 | 期望行为 |
|---|---|
| `page` 越界（如 999） | 返回空 `items` 与正确的 `total`，不是错误 |
| `size` 为 0 或负数 | 收敛到默认值 20 |
| `size` 超过 100 | 收敛到 100（与任务模块口径一致） |
| 搜索词含 SQL 通配符（`%`、`_`） | 按字面匹配，不当作通配符（转义或不用 LIKE） |
| 搜索词含前后空格 | 先 trim；空串等同于「不筛选」 |
| 搜索结果为空 | 200 + 空列表，`total=0` |
| 数据在翻页过程中被并发修改 | 不加锁；`total` 是查询时刻的快照 |

## Requirements *(mandatory)*

- **FR-001**：知识库与会话列表 MUST 支持 `page` + `size` 分页，响应为 `PageDto`。
- **FR-002**：两者 MUST 支持关键词筛选（知识库匹配标题与文件名，会话匹配标题）。
- **FR-003**：分页与筛选 MUST 在 SQL 层完成，MUST NOT 加载全量到内存再切片。
- **FR-004**：**导出链路 MUST 继续拿到全量数据** —— `ChatExportContributor` 与
  `KnowledgeExportContributor` 依赖全量 `list()`，因此 `list()` 必须保留，
  分页是新增能力而不是替换。
- **FR-005**：分页参数越界的收敛行为 MUST 与任务模块一致（非正 size → 20，>100 → 100）。
- **FR-006**：会话分页时消息条数 MUST 仍然正确（只对当前页做一次分组查询，避免 N+1）。
- **FR-007**：前端两个页面 MUST 有搜索框与分页控件；搜索词变化时页码 MUST 归零。
- **FR-008**：本阶段 MUST NOT 实现跨模块全局搜索 —— 它需要聚合 5 个模块、设计
  排序与权重，是独立问题（见 Assumptions）。

## Success Criteria

- **SC-001**：`./mvnw -B verify` 全绿；新增测试覆盖分页边界收敛、关键词筛选、
  导出仍拿全量、会话分页后消息数正确。
- **SC-002**：`npm run test:logic` 全绿，覆盖「搜索词变化归零页码」。
- **SC-003**：真机：知识库翻页 + 搜索；对话页搜索会话；导出功能不受影响。

## Assumptions

- **保留 `list()` 而不是删掉**：导出需要全量。删除它会让导出变成「只能导出第一页」，
  那是比现在更糟的结果。分页接口用 `search()`，两者职责分明。
- 不做全局搜索。它需要决定：搜哪些模块、每模块返回几条、怎么排序、关键词高亮在哪做。
  这些选择每一个都会显著改变用户体验，值得单独一个阶段。
- 不做增量加载（无限滚动）：分页控件已经够用，而无限滚动会带来「回到顶部」的额外需求。
