# Feature Specification: 阶段 9 — 可靠提醒

**Feature Branch**: `009-reliable-reminders`

**Created**: 2026-10-25

**Status**: Draft

**Input**: 用户需求：「按照建议的几个缺口，帮我逐个实现」的第三项 —— 提醒只靠页面内 30 秒轮询，
用户不在日程页（或浏览器最小化）时，到点的提醒**根本没有存在感**。

## 背景：现在的提醒只在「正看着页面」时才存在

阶段 4 的提醒链路是完整的：任务/日程 → 扫描物化 `reminder` 行 → 前端每 30 秒拉一次未读到点提醒 → 页面顶部显示徽标。
问题在最后一环：**徽标只在日程页可见**。用户在对话页写东西、或把窗口切走时，提醒等于不存在。

本阶段补的是**送达层**：让到点的提醒主动出现在用户眼前，并且在浏览器不允许时明确告知限制，
而不是让用户以为"没提醒就是没事"。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 到点主动提醒（Priority: P1）

作为用户，我希望到了提醒时间，即使我正在别的页面工作，也能被通知到。

**Why this priority**：这是本阶段唯一要解决的问题。「提醒不响亮」等于没有提醒。

**Independent Test**：授予通知权限后，把一条提醒的时间设为当前时间，等一次轮询（≤30 秒），
浏览器弹出系统通知，内容含提醒标题与时间。

**Acceptance Scenarios**：

1. **Given** 通知权限已授予、页面在后台（不可见），**When** 轮询拿到一条到点提醒，**Then** 弹出**系统通知**，含来源（任务/日程）、标题与到点时间。
2. **Given** 通知权限已授予、页面**可见**，**When** 轮询拿到到点提醒，**Then** 显示**站内提示**（不弹系统通知）—— 用户已经看着屏幕，系统通知是多余的干扰。
3. **Given** 同一条提醒在同一页面会话内已经通知过，**When** 下一次轮询仍然返回它（未标记已读），**Then** **不再重复通知**。
4. **Given** 用户点击系统通知，**When** 通知被点击，**Then** 浏览器窗口获得焦点并打开日程页。
5. **Given** 一次轮询拿到多条新提醒，**When** 逐个通知，**Then** 每条各通知一次；超过 3 条时合并为一条汇总通知（避免通知风暴）。

---

### User Story 2 - 权限与降级要诚实（Priority: P1）

作为用户，我需要知道"通知到底生效没有"，以及"为什么没生效"。否则我会误以为系统在盯着，实际什么都没发生。

**Why this priority**：与 US-1 同为 P1。没有权限状态可见性的通知功能，比没有通知更危险 ——
它制造了虚假的安全感。

**Independent Test**：在三种权限状态（未申请 / 已授予 / 已被拒绝）下打开日程页，分别看到对应的引导与状态。

**Acceptance Scenarios**：

1. **Given** 通知权限尚未申请，**When** 打开日程页，**Then** 显示「开启浏览器通知」按钮，且**不自动**弹权限请求。
2. **Given** 用户点击开启按钮，**When** 浏览器询问权限，**Then** 授权后按钮变为「通知已开启」状态，且页面刷新后仍显示已开启。
3. **Given** 权限被用户拒绝，**When** 之后打开日程页，**Then** 显示「浏览器已阻止通知」以及**如何恢复**的说明，且**不再自动请求**权限。
4. **Given** 权限被拒绝或未授予，**When** 轮询拿到到点提醒，**Then** 页面内徽标与列表**照常**工作（降级不丢失信息）。
5. **Given** 浏览器不支持 Notification API，**When** 打开日程页，**Then** 显示「当前浏览器不支持」而不是一个点了没反应的按钮。

## Edge Cases

| 场景 | 期望行为 |
|---|---|
| 权限 `default`（未决定） | 只显示按钮，不自动请求 —— 自动弹窗在多数浏览器里会被直接拒绝 |
| 权限 `denied` | 不再调用 `requestPermission`（调用也不会弹窗），只给恢复说明 |
| 页面可见时到点 | 用站内提示，不弹系统通知 |
| 同一条提醒多次轮询返回 | 只通知第一次（页面会话内去重） |
| 用户刷新页面后，同一条未读提醒仍在 | **允许再次通知** —— 用户可能没看到；这比"第一次之后永远静默"安全 |
| 一次拿到 4 条以上 | 合并为一条「你有 N 条提醒到点」的汇总通知 |
| 通知构造抛异常（部分浏览器的安全限制） | 静默降级为站内提示，不打断轮询 |
| 用户点了「标记已读」后再到点 | 不通知（服务端 `dueOnly` 只返回未读） |
| 服务端不可用 | 轮询静默失败（沿用阶段 4 行为），不弹错误 |

## Requirements *(mandatory)*

- **FR-001**：系统 MUST 在权限已授予时，对到点提醒发出系统通知（浏览器通知）。
- **FR-002**：系统 MUST 在页面可见时改用**站内提示**，不弹系统通知。
- **FR-003**：同一条提醒 MUST 在同一页面会话内只通知一次；刷新页面后重置该判断。
- **FR-004**：一次拿到超过 3 条新提醒时 MUST 合并为一条汇总通知。
- **FR-005**：点击系统通知 MUST 让窗口获得焦点并导航到日程页。
- **FR-006**：权限请求 MUST 只由用户手势触发（点击「开启浏览器通知」），MUST NOT 在页面加载时自动请求。
- **FR-007**：权限被拒绝后 MUST NOT 再次调用 `requestPermission`，并 MUST 展示恢复指引。
- **FR-008**：无论权限状态如何，页面内提醒列表与徽标 MUST 保持原有功能（不因通知失败而退化）。
- **FR-009**：浏览器不支持通知时 MUST 明确告知，MUST NOT 展示无效按钮。
- **FR-010**：通知构造失败 MUST NOT 中断轮询，也 MUST NOT 产生未捕获异常。

## Success Criteria *(mandatory)*

- **SC-001**：权限授予 + 页面不可见时，命中的提醒 100% 触发一次系统通知（以构造 `Notification` 的调用为证）。
- **SC-002**：页面可见时，命中提醒 0 次系统通知、100% 出现站内提示。
- **SC-003**：同一条提醒连续 3 次轮询返回，通知次数为 1。
- **SC-004**：4 条同时到点 → 1 条汇总通知（而不是 4 条）。
- **SC-005**：三种权限状态下，页面分别显示正确状态文案（按钮 / 已开启 / 已阻止 + 指引）。
- **SC-006**：`denied` 状态下不产生任何 `requestPermission` 调用。

## Assumptions

- **不做后台送达**：用户已明确选择「浏览器通知 + 降级」。应用与页面都关闭时收不到 —— 这是本阶段**已知且必须显式告知**的限制（真后台送达需要 Service Worker + Web Push + HTTPS/VAPID，本地单机成本远高于收益）。
- **不做通知声音/角标/桌面应用**：超出浏览器 API 的可控范围或需要额外壳。
- **不改后端**：提醒的物化、去重、已读状态在阶段 4 已经做对了；本阶段只解决送达。
- **去重不做持久化**：页面会话内去重（内存 Set）足够。持久化会让"标记已读失败的提醒"永远静默，比重复通知更糟。

## 明确不含

| 不做的事 | 依据 |
|---|---|
| Service Worker / Web Push / 离线推送 | 用户已选降级方案；本地单机无 HTTPS 与推送服务 |
| 通知优先级/分组/静音时段 | 无对应使用场景，且需要设置界面 |
| 服务端推送通道（SSE/WebSocket 推提醒） | 页面关闭时同样无效，收益与轮询相同而复杂度更高 |
| 修改提醒的物化与去重逻辑 | 阶段 4 已验证，本阶段不动后端 |
| 桌面通知的富交互（按钮/回复） | 需要 Service Worker |
