# Feature Specification: 阶段 4 — 日程与定时提醒

**Feature Branch**: `005-calendar-reminders`

**Created**: 2026-10-14

**Status**: Draft

**Input**: 用户需求：「阶段 4：日程和定时提醒（Spring Scheduling）」+ 三项已确认的边界决策：
① 提醒送达方式 = **落库 + 前端轮询**；② 日程与任务**都能提醒**；③ 重复规则 = **一次性 + 简单重复（每天/每周/每月/工作日）**。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 创建日程（Priority: P1）

作为用户，我希望把「明天 10 点和张三开会」记下来，并能在日历上看到它。

**Why this priority**：日程是本阶段的数据基础，提醒依附于它。

**Independent Test**：创建一个日程后，查询某时间区间能把它取出来，且字段（标题、起止、全天、地点）与创建时一致。

**Acceptance Scenarios**：

1. **Given** 系统就绪，**When** 创建一次性日程，**Then** 返回日程标识，且能在对应时间区间内查到。
2. **Given** 全天日程，**When** 创建，**Then** 起止时间落在当天 00:00~次日 00:00，且标记为全天。
3. **Given** 结束时间早于开始时间，**When** 创建，**Then** 返回参数错误，零写入。
4. **Given** 标题为空或超长，**When** 创建，**Then** 返回参数错误，零写入。

---

### User Story 2 - 重复日程（Priority: P1）

作为用户，我希望「每周一 9 点站会」只记一次，而不是记 52 次。

**Why this priority**：重复是日程区别于普通待办的核心价值。

**Independent Test**：创建一条每周重复的日程，计算给定时间区间内的发生时刻，结果符合规则且**同一次计算可重复**。

**Acceptance Scenarios**：

1. **Given** 每周重复的日程，**When** 计算未来若干次发生时刻，**Then** 每次间隔恰好 7 天且时刻不变。
2. **Given** 工作日重复的日程，**When** 计算发生时刻，**Then** **只落在周一至周五**，跳过周末。
3. **Given** 每月 31 日重复的日程，**When** 计算到 2 月，**Then** 取该月**最后一天**（2 月 28/29 日）而不是跳过该月。
4. **Given** 设置了重复截止日期的日程，**When** 计算超过截止日期，**Then** 不再产生新的发生时刻。
5. **Given** 重复日程，**When** 同一区间重复计算两次，**Then** 结果**完全一致**（纯函数，无隐藏状态）。

---

### User Story 3 - 到点提醒（Priority: P1）

作为用户，我希望日程快到的时候能被提醒，而不是错过会议。

**Why this priority**：这是本阶段的核心价值出口；没有它，日程只是另一个列表。

**Independent Test**：把系统时间推进到提醒时刻，扫描后能取到该提醒；再扫描一次，**不会产生第二条**。

**Acceptance Scenarios**：

1. **Given** 一个 10:00 开始、提前 15 分钟提醒的日程，**When** 时间到达 09:45，**Then** 该提醒出现在「待提醒」列表中。
2. **Given** 已生成的提醒，**When** 重复扫描（模拟重启或多次调度），**Then** 提醒条数**不变**（幂等）。
3. **Given** 提醒尚未到点，**When** 查询待提醒列表，**Then** **不包含**它。
4. **Given** 用户读过该提醒，**When** 再次查询，**Then** 它不再出现在待提醒列表，但记录仍在（可追溯）。
5. **Given** 已完成的任务，**When** 扫描，**Then** **不产生**提醒（已完成的事不该再提醒）。

---

### User Story 4 - 任务也能提醒（Priority: P1）

作为用户，我不希望「任务」和「日程」是两个割裂的世界 —— 我在任务上写的截止时间，到点也该提醒我。

**Why this priority**：用户已明确选择「两者都能提醒」。若不做，用户会在两个地方各写一遍时间。

**Independent Test**：给任务设置截止时间，推进时间后扫描，待提醒列表中出现该任务的提醒，且来源标注为任务。

**Acceptance Scenarios**：

1. **Given** 有截止时间的未完成任务，**When** 时间进入提醒窗口，**Then** 生成一条提醒，来源类型为「任务」。
2. **Given** 该任务被标记完成，**When** 扫描，**Then** 不再为其生成新提醒；**已生成的**未读提醒**仍保留**（不静默消失，避免用户困惑）。
3. **Given** 任务的截止时间被修改，**When** 扫描，**Then** 按新时间生成提醒，旧时间若已生成提醒则保留（历史不可篡改）。
4. **Given** 同一任务，**When** 重复扫描，**Then** 同一发生时刻只对应一条提醒。

---

### User Story 5 - 在对话中安排日程（Priority: P2）

作为用户，我希望直接说「帮我记一下明天下午三点开会」，助手真的把日程建好。

**Why this priority**：与阶段 2/3 一致的自然语言入口；但 REST 已能满足核心需求。

**Independent Test**：在对话中发出建日程的指令，助手调用工具，数据库中出现该日程。

**Acceptance Scenarios**：

1. **Given** 对话中，**When** 说「明天下午三点开会」，**Then** 日程被真实创建，且回复告知已创建。
2. **Given** 存在日程，**When** 让助手删除它，**Then** **不直接删除**，而是生成待人工确认事项（复用阶段 2 的确认机制）。
3. **Given** 让助手「看看今天有什么安排」，**When** 调用查询工具，**Then** 返回当天的日程。

---

### User Story 6 - 前端轮询提醒（Priority: P2）

作为用户，我希望页面上能自动出现到点的提醒，不需要我手动刷新。

**Why this priority**：用户已确认采用轮询方式；它是提醒的可见出口。

**Independent Test**：页面打开时，到点的提醒在下一个轮询周期内出现。

**Acceptance Scenarios**：

1. **Given** 页面打开且存在到点提醒，**When** 轮询周期到达，**Then** 提醒出现在页面上。
2. **Given** 用户点击「知道了」，**When** 轮询再次执行，**Then** 该提醒不再出现。
3. **Given** 轮询请求失败（后端不可用），**When** 页面仍在，**Then** 不弹错误弹窗轰炸用户，仅静默重试。

---

### Edge Cases

- **扫描间隔与提前量的关系**：若提前量小于扫描间隔，提醒仍**必须**被补上（不能因为扫描时已过点就丢弃）——过点但未读的提醒仍需展示。
- **系统时间回拨**：时间被调回过去时，不得重复生成已在未来生成过的提醒（靠唯一键而非时间比较保证）。
- **跨月/跨年重复**：每月重复在 1 月 31 日之后是 2 月末、再回到 3 月 31 日（按原始「每月第 N 天」语义）。
- **闰日**：每月 29 日重复在平年 2 月取 2 月 28 日。
- **超长区间查询**：查询区间过大时必须限制返回条数，而不是把全部日程拉出来。
- **重复截止日期早于开始时间**：参数错误，零写入。
- **删除日程**：其提醒必须一并清理，不留「有提醒无日程」的孤儿记录。
- **同一日程的多个发生时刻**：各自独立提醒，互不影响。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**：系统 MUST 提供日程的创建、查询（按时间区间）、修改、删除。
- **FR-002**：日程 MUST 含：标题、描述、地点、是否全天、开始时间、结束时间、创建/更新时间。
- **FR-003**：结束时间 MUST NOT 早于开始时间；全天日程的语义 MUST 明确（当天 00:00 至次日 00:00）。
- **FR-004**：系统 MUST 支持重复规则：不重复 / 每天 / 每周 / 每月 / 工作日。
- **FR-005**：重复规则 MUST 可设置截止日期（含）与提前提醒量。
- **FR-006**：重复发生时刻的计算 MUST 是**纯函数**（给定规则与区间，结果确定且无副作用）。
- **FR-007**：每月重复 MUST 处理「当月无该日」的情况：取当月最后一天，而不是跳过该月。
- **FR-008**：工作日重复 MUST 只落在周一至周五。
- **FR-009**：系统 MUST 定期扫描并**物化**提醒记录；扫描 MUST 幂等（重复扫描不产生重复提醒）。
- **FR-010**：提醒 MUST 记录：来源类型（日程/任务）、来源标识、标题快照、提醒时刻、状态、生成/读取时间。
- **FR-011**：同一「来源 + 发生时刻」MUST 至多对应一条提醒（数据库层唯一约束）。
- **FR-012**：提醒状态 MUST 至少区分：待提醒 / 已读 / 已取消。
- **FR-013**：系统 MUST 为**有截止时间且未完成**的任务生成提醒（FR-013）。
- **FR-014**：任务完成后 MUST 不再为其生成新提醒；已有的未读提醒 MUST NOT 被静默删除。
- **FR-015**：已过提醒时刻但未读的提醒 MUST 仍可被展示（不因过期而丢弃）。
- **FR-016**：日程删除时 MUST 同时取消其提醒。
- **FR-017**：系统 MUST 提供「待提醒列表」查询（仅返回到点且未读的）。
- **FR-018**：系统 MUST 提供「标记已读」能力，且标记操作 MUST 幂等。
- **FR-019**：调度 MUST 由数据库状态驱动（不依赖内存中的定时任务），使**重启后行为一致**。
- **FR-020**：扫描逻辑 MUST 接受**可注入的时间**，以便在不等待真实时间的前提下测试。
- **FR-021**：日程删除属于不可逆操作，由 Agent 发起时 MUST 经人工确认（复用阶段 2 机制）。
- **FR-022**：系统 MUST 以 Agent 工具形式暴露日程能力（创建、查询、删除）。
- **FR-023**：所有新接口 MUST 使用既有统一响应结构；MUST NOT 向前端暴露 JPA 实体。
- **FR-024**：所有写操作 MUST 经过 Service 层；数据库结构变更 MUST 由 Flyway 迁移管理。
- **FR-025**：前端 MUST 以轮询方式获取到点提醒，且轮询失败 MUST NOT 打断用户。
- **FR-026**：前端 MUST 支持日程列表、创建与删除。

**范围边界（本阶段明确不含）**：

- 不含推送通知（SSE / 浏览器系统通知 / 邮件 / IM）—— 用户已确认只做轮询。
- 不含完整 RRULE（不含「每月第二个周二」「每两个工作日」这类规则）。
- 不含多时区与夏令时处理（统一使用系统时区）。
- 不含日历订阅（CalDAV / ICS 导入导出）。
- 不含日程邀请、参与者、会议室。
- 不含提醒的贪睡（snooze）与自定义提醒音。
- 不含与外部日历的双向同步。
- 不含基于位置的提醒。

### Key Entities

- **CalendarEvent（日程）**：标题、描述、地点、全天标记、起止时间、重复规则、重复截止、提前提醒量。
- **Reminder（提醒）**：来源类型与标识、标题快照、发生时刻、提醒时刻、状态、读取时间。**来源可以是日程或任务**。
- **RecurrenceRule（重复规则）**：类型（不重复/每天/每周/每月/工作日）+ 截止日期。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：重复规则计算是纯函数 —— 同一输入计算两次，结果**逐元素相等**。
- **SC-002**：工作日重复在任一跨度 ≥ 30 天的区间内，落在周末的发生时刻数为 **0**。
- **SC-003**：每月重复的日程在跨 12 个月的区间内，**每个月恰好有一次**发生时刻（不跳月）。
- **SC-004**：连续扫描 N 次（N ≥ 5）后，`reminder` 表行数与扫描 1 次**完全相等**。
- **SC-005**：应用重启后再次扫描，`reminder` 表行数**不变**。
- **SC-006**：任务标记为完成后，针对**该任务**新生成的提醒数为 **0**。
- **SC-007**：删除日程后，该日程的提醒条数**为 0**。
- **SC-008**：同一「来源 + 发生时刻」在数据库中的提醒条数**恒为 1**（唯一约束生效）。
- **SC-009**：非法输入（结束早于开始、空标题、重复截止早于开始）导致的 `calendar_event` 变化行数为 **0**。
- **SC-010**：所有时间相关测试**不依赖真实等待**（无 `Thread.sleep`），且无网络、无外部服务。

## Assumptions

- 统一使用**系统时区**，不做时区转换（本地单用户场景）。
- 「全天」的定义：`starts_at` 为当天 00:00、`ends_at` 为次日 00:00，`all_day = true`。
- 提醒提前量默认 **15 分钟**，可按日程配置；任务提醒用全局默认值。
- 扫描间隔默认 **60 秒**，扫描窗口默认**未来 24 小时**（确保提前量小于窗口时不漏）。
- 提醒**物化**而非即时计算：物化后才能承载「已读」状态与审计痕迹，这是无法从事件本身推导的信息。
- 重复日程的**历史发生时刻**也参与提醒物化（只要落在扫描窗口内）—— 与「过点未读仍展示」保持一致。
- 阶段 2 的确认机制需要**泛化**（当前只支持任务类操作），日程删除将作为新的一种待确认动作类型接入。
