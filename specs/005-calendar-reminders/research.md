# Research: 阶段 4 — 日程与定时提醒

> 本篇记录的是**设计层面的取舍**与**沿用既有结论**的部分。本阶段无需核实新的外部 API
> （只用 Spring 自身的 `@Scheduled`），因此没有 jar 反编译记录，取而代之的是「为什么这么选」。

## R-01 提醒用「物化」而不是「即时计算」

**Decision**：定时扫描把提醒**写入 `reminder` 表**，前端查询该表；不在查询时现算。

**Rationale**：
- 「已读」是**无法从日程本身推导**的状态。若现算，每条提醒都是临时的，读完就忘了读没读。
- 物化后有审计痕迹：能回答「这条提醒什么时候生成、什么时候被读」。
- 物化让「同一发生时刻只有一条」这条约束可以落在**数据库唯一键**上 —— 而不是靠代码里的小心。

**Alternatives considered**：查询时按 `remind_at <= now` 现算 → 无法承载已读状态、无法审计、且每次查询都要跑一遍重复规则计算（重复规则计算不便宜）。

## R-02 调度用「DB 状态驱动」而不是「内存定时任务」

**Decision**：`@Scheduled(fixedDelay)` 周期性调用 `scan(now)`；**不**为每条提醒注册一个内存 `TaskScheduler` 任务。

**Rationale**：
- 内存任务在**重启后全部丢失**，用户会静默地收不到提醒 —— 这是最难发现的一类故障（没有任何报错，只是"没提醒"）。
- 状态在库里时，重启后下一次扫描会自然地把该补的补上。
- DB 驱动让扫描逻辑变成一个**纯方法** `scan(Instant now)`，测试可以直接传时间调用，
  不必真的等一分钟 —— 这是 FR-020 与 SC-010 的实现基础。

**代价（已记录）**：提醒的时刻精度受扫描间隔限制（默认 60 秒）。对个人日程场景完全够用；
若将来要求秒级精度，应在扫描间隔上做文章，而不是改成内存任务。

## R-03 时间维度必须可注入，否则没法测

**Decision**：所有涉及「现在」的代码通过注入的 `Clock` 获取时间；`scan(Instant now)` 显式接收时间参数。

**Rationale**：
- 「到点提醒」这类逻辑如果直接调 `Instant.now()`，测试就只能 `Thread.sleep` 等到点。
  那会让测试**又慢又不稳定**（CI 上尤其明显），最终结果是没人愿意跑它。
- 显式传时间还让「时间回拨」「跨月」「闰日」这些边界变得**可测**：
  传一个特定时刻进去即可，不需要操纵系统时钟。

## R-04 幂等靠数据库唯一键，而不是靠「先查再插」

**Decision**：`reminder` 表上建唯一约束 `(source_type, source_id, occurrence_at)`；
扫描时用「插入并忽略冲突」的语义，不用「先 SELECT 判断存在再 INSERT」。

**Rationale**：
- 「先查再插」在并发下必然出现竞态（两个线程都查到"不存在"，然后都插入）。
  本阶段虽然只有一个调度线程，但**手动触发扫描 + 定时扫描**同时发生是现实可能的。
- 唯一键把「只能有一条」这件事变成**数据库的职责**，代码侧只需处理冲突。
- 这也让「时间回拨」变得安全：判断依据是「这个发生时刻有没有提醒」，而不是「现在的时间比上次大」。

**Alternatives considered**：给扫描加分布式锁 → 单机单用户场景纯属过度设计。

## R-05 任务提醒：扫描时统一生成，而不是在任务变更时事件通知

**Decision**：扫描时**同时**看 `calendar_event` 的近期发生时刻与 `task` 的近期截止时间，
统一生成提醒；**不**在任务保存时发布事件去创建提醒。

**Rationale**：
- 事件驱动要求「任务变更」这条路径**永远**会发事件 —— 一旦漏发（新增一条改 due_at 的代码路径忘了发），
  提醒就静默缺失。而扫描式是**兜底重算**，任何原因导致的漏发都会在下一轮扫描被补上。
- 扫描式避免让 `task` 模块依赖 `calendar`（或引入事件类），模块方向更干净：
  只有 `calendar` **只读**地依赖 `task` 的查询能力。
- 天然幂等：每次扫描都是「确保应有的提醒都存在」，与唯一键配合后是纯 upsert 语义。

**Alternatives considered**：`task` 发布 `TaskScheduleChangedEvent`，`calendar` 监听 → 需要在 task 模块新增事件发布点，且漏发会静默失败 → 否决为**主路径**，但保留为将来的优化（可降低提醒的延迟）。

## R-06 重复规则自实现，不引入日历库

**Decision**：只支持 `NONE / DAILY / WEEKLY / MONTHLY / WEEKDAYS`，自己实现「给定规则 + 区间 → 发生时刻列表」。

**Rationale**：
- 完整 RRULE（`ical4j` 等）要引入新依赖，并处理时区、夏令时、`BYSETPOS` 等复杂语义 ——
  对一个本地个人日程来说是明显的过度设计（宪法原则 I）。
- 这四类规则覆盖个人日程的绝大多数场景，且实现是**纯函数**，可以逐条断言（SC-001/002/003）。
- 边界清晰：`MONTHLY` 在当月无该日时取**当月最后一天**（用户不会因为"2 月没有 31 号"就丢掉整个 2 月）。
  这个语义必须写进代码注释，否则下一个维护者会以为是个 bug。

## R-07 阶段 2 的确认机制需要泛化（本阶段的前置重构）

**Decision**：把 `ConfirmationService` 与 `TaskConfirmation*` 从 `agent/confirmation` 迁到 `common/confirmation`，
并引入 `ConfirmationActionHandler` SPI：各业务模块注册自己的动作处理器，`ConfirmationService` 只负责
「令牌 / 有效期 / 单次性 / 原子占位」这些**与业务无关**的机制。

**Rationale**：
- 当前 `ConfirmationService.applyPayload` 是一个 `switch (action)`，**硬编码了三种任务动作**。
  日程删除要接进来就必须改这个 switch —— 每加一个高风险操作就改一次通用服务，
  这正是 SPI 要解决的问题。
- 迁到 `common` 与阶段 3 把 `ToolExecutor` 迁到 `common/ai/tool` 是同一个判断：
  **这是跨业务模块的公共机制，不是某个模块的私有实现**。
- `ConfirmationAction` 的取值在数据库里有 CHECK 约束，新增取值需要配套迁移（V5）。

**代价（已记录）**：这是一次涉及阶段 2 代码的重构，需要保证阶段 2 的 21 个测试仍然全绿。
若重构导致阶段 2 行为变化，属于回归，必须修回去而不是改测试。

## R-08 沿用阶段 2/3 已锁定的结论（不重复踩坑）

| 结论 | 来源 |
|---|---|
| 工具基础设施在 `common/ai/tool`，各业务模块共用 | 阶段 3 |
| 工具经 `ToolContributor` SPI 注册，`chat` 模块零改动 | 阶段 2 |
| 工具需要上下文时用 `ToolContext` 注入，不用 `ThreadLocal` | 阶段 2 |
| 写操作的集成测试断言口径是**数据库受影响行数** | 阶段 2 |
| 高风险操作必须经人工确认，且**工具集合中不存在确认类工具** | 阶段 2 |
| 集成测试用脚本化桩 `ChatModel` 驱动工具调用，无网络无密钥 | 阶段 2 |
