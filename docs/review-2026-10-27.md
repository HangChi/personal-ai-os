## 一、必修清单（按影响面排序）

### 1. 摘要把模型调用包在数据库事务里 —— 全站 5 秒超时的最现实来源

`chat/service/ChatSummaryService.java:123-130`（`transactionTemplate.executeWithoutResult` → `doRefresh` → `summarize`）

`doRefresh` 在整个事务内调用非流式模型（一次完整 HTTP，默认无超时）。Hikari `maximum-pool-size: 10`，`connection-timeout: 5000`。模型慢 10-60 秒时，每个摘要任务钉住一条连接，正常请求（读消息、`requireSession`）在 5 秒后失败——表现是"聊着聊着整个应用卡死"，而日志里只有一行 `debug`。

**修法**：拆三段。事务 A 读 `session` + `pending` 快照并结束 → **事务外**调模型 → 事务 B 重新加载、校验 `summaryUptoSeq` 未变再 `applySummary`（该方法已有单调前进保护，天然适配）。同时给摘要调用设超时。

### 2. 确认链路的两种失败方式都是错的

`common/confirmation/ConfirmationService.java:103`、`:123-140`；`task/service/TaskService.java:177-188`

```java
@Transactional(noRollbackFor = BusinessException.class)   // :103
...
int claimed = repository.compareAndSetStatus(id, PENDING, CONFIRMED, now);  // :123
int affected = registry.require(...).execute(...);                          // :130
```

`noRollbackFor` 本是为 `:114-118` 的"过期标记要落库"写的，但它作用于**整个方法**，于是：

- **失败被记成成功**：handler 抛 `BusinessException`（如 MCP server 不可用、批量删除超 50 条）时，`CONFIRMED` 已被提交。记录显示"已执行"、实际一行未改，令牌一次性作废，用户再点得到"该确认已执行，无法再次执行"——操作**永久丢失**。
- **优雅降级变成 500**：`:134` catch `ResourceNotFoundException` 想置 `CANCELLED`，但 `reschedule`（`TaskService:178` `@Transactional`）在共享事务上抛了 RuntimeException → 事务被标 `rollbackOnly` → `:136` 的写入与整个事务在提交时抛 `UnexpectedRollbackException` → 兜底 500。这条路径**必然触发**：确认一个 `SCHEDULE_TASK`，而任务在确认前被删；或 MCP handler 的 `:57` 抛 `ResourceNotFoundException`。

**修法**：把"占位"和"执行"拆开，不要靠注解调参。`REQUIRES_NEW` 提交占位 → 事务外执行 handler → 另起 `REQUIRES_NEW` 回写结果（成功/取消/失败）。这同时消掉下面的第 6 条（外部调用在事务内）。

### 3. 修改日程后旧提醒照常触发

`calendar/service/CalendarEventService.java:91-150`（`update` 完全不碰 `reminder`）；`calendar/repository/ReminderRepository.java:47-56`（`ON CONFLICT ... DO NOTHING`）

`update` 改完 `startsAt`/`title`/`reminderLeadMinutes` 后直接返回，提醒行不被清理也不被更新，于是：

- 改时间 → 旧 `occurrence_at` 的提醒保留并**照常弹出旧时间**，新时间再插一条 → 用户收到两条，一条是错的；
- 改标题 → 提醒里存的是快照，弹旧标题；
- 改提前量 → UPSERT 冲突时 `DO NOTHING`，`remind_at` 不更新，改动静默失效。

**修法**：`update` 末尾 `reminderRepository.deleteBySource(CALENDAR_EVENT, id)`（复用 `delete()` 已有的写法），下一轮扫描按新规则重建；或把 UPSERT 改成 `DO UPDATE SET title=excluded.title, remind_at=excluded.remind_at WHERE status='PENDING'`。

### 4. 提前量上限 7 天，扫描窗口只有 24 小时

`calendar/dto/CreateEventRequest.java:48`（`@Max(10080)`）vs `calendar/service/ReminderScanner.java:73-75`（`windowEnd = now.plus(scanLookahead)`，默认 24h）

类注释自己写了"窗口必须覆盖提前量"，代码里没有任何校验。建一个 5 天后、提前 7 天提醒的日程：它要等到进入 24h 窗口才被物化，此时 `remind_at` 已是 6 天前 → 提醒晚到最多 6 天，且一出现就是过期状态。

**修法**：`windowEnd = now.plus(max(scanLookahead, 最大 lead))`，或在 create/update 校验 `lead <= lookahead` 并把 `@Max` 收到 lookahead 内。前者更好：不削减用户能力。

### 5. 流式超时既不发 error 帧，也不落助手消息

`chat/service/ChatCompletionService.java:64`、`:258-264`

`onTimeout` 里只 `terminated.set(true)` + `emitter.complete()`：客户端最后收到的是 `delta` 或 `ping`，然后连接静默关闭，前端只能一直转圈到自己的超时；更严重的是 `terminated=true` 让正常收尾分支（`finisher.attachCitations/afterDone`）全部跳过，而助手消息依赖 Advisor 在流正常终止时写入——订阅被 dispose 后，**用户消息已落库、助手回复永久丢失**，下一轮上下文里出现一条没有回答的提问，摘要还会把它当事实压进去。

`SSE_TIMEOUT_MILLIS = 120_000` 是整条流的上限，而 `ThinkingLevel.DEEP` 的思考预算 8192 在思考型模型上很容易超过。

**修法**：`onTimeout` 里先发 `EVENT_ERROR`（新增 `AI_TIMEOUT` 码）再 `complete()`，并走与 `:222-233` 相同的失败收尾（至少落一条标记为中断的助手消息）；超时按 `thinkingLevel` 分档（120/180/300s），另加"首字节超时"独立判定。

### 6. 客户端断连后上游不取消，模型继续烧 token

`chat/service/ChatCompletionService.java:388-394`

`send()` 捕获 `IOException | IllegalStateException` 只打 `debug`，`terminated` 不变、订阅不 dispose。容器不一定立刻回调 `onCompletion`，于是模型继续生成到自然结束或 120 秒超时，每个 delta 都往死 socket 写并抛异常。同类窗口：`:214` 先 `subscribe`、`:256` 才 `subscriptionRef.set`、`:258` 之后才注册回调——客户端在 `start` 后立刻断开时，`disposeQuietly(null)` 是 no-op。

**修法**：`send` 失败即触发终止回调（置 `terminated`、停心跳、`closeStream`、dispose）；先注册 `onTimeout/onError/onCompletion` 再 `subscribe`，并在 `compareAndSet(null, subscription)` 后发现已 terminated 立刻 dispose。

### 7. 登录是唯一没有防护的入口

`common/web/RateLimitFilter.java:49-52`；`common/auth/AuthController.java:54-65`；`application.yml:14-20`

- `GUARDED_PATHS` 只有 `stream`/`uploads`/`documents` 三条——**"会花钱的端点"防住了，"进门的端点"没防**。没有失败计数、没有锁定、没有指数退避。BCrypt 只把速率压到约 10 次/秒，6 位数字口令几小时内必然命中。
- 会话 Cookie 只有 `same-site: lax` + `http-only: true`，**没有 `secure`**。反代漏配 HTTPS 时 `JSESSIONID` 走明文，而 CSRF 又是关闭的，等于拿到会话即拿到全部权限。
- 顺带：`RateLimitFilter:69` 用 `request.getRequestURI()`（未解码）匹配路径，`POST /api/v1/chat/%75ploads` 会被控制器正常处理却跳过令牌桶。

**修法**：① 登录纳入限流，单用户场景只需一个全局失败计数器（连续 5 次锁 60 秒，成功清零）；② `secure: ${SESSION_COOKIE_SECURE:true}`，本地开发用环境变量关；③ 路径匹配改用解码后的 path。

### 8. 知识库上传在数据库事务内做解析 + 全量嵌入

`knowledge/service/KnowledgeDocumentService.java:74-131`（`ingest`）、`:230-280`（`update`），两处都是 `@Transactional`

5MB 文档可产生数百块 → 数百次 embedding HTTP 调用，全部在**持有一条连接的事务里**。池是 10，10 个并发上传即占满，全站连 `/chat` 流式一起排队。它同时放大了下面这些问题：PDF 全内存解析、docx 无膨胀上限、视觉模型识别——它们都跑在同一条被钉住的连接上。

**修法**：解析 + 切块 + `vectorStore.add` 移到事务外，事务只包住 `knowledge_document` 的两条 SQL；或改为"先落 PENDING → 异步索引 → 回填 STATS"。

### 9. 替换文档后，引用里的标题永远是旧的

`knowledge/service/KnowledgeDocumentService.java:250` → `:296-300` → `:282`

```java
List<Document> parsed = readerFactory.create(ext, ct, bytes, baseMetadata(document)).get();  // :249 旧标题
...
document.replaceContent(stripExtension(filename), filename, ...);   // :284 才换标题
```

`baseMetadata` 取的是**更新前**实体的 `title`，向量元数据里的 `document_title` 就此固化。此后每次检索命中、每条引用、`ask` 的来源名全是旧标题，且没有入口能修（除非再上传一次）。

**修法**：先算新 title 再构造 metadata（把 `chunk(parsed, documentId, title)` 改成显式传标题）。

### 10. 全局搜索对含大写字母的关键词恒不命中

`common/search/SearchPatterns.java:30-36` + `task/TaskSearchContributor.java:44-46`（calendar/knowledge/memory/chat 同构）

```java
String pattern = SearchPatterns.likePattern(keyword);        // 未小写
String needle  = keyword.toLowerCase(Locale.ROOT);           // 这里小写了，说明本意是忽略大小写
builder.like(builder.lower(root.get("title")), pattern, ESCAPE)   // 列被 lower，模式没有
```

搜 `Vue`、`API`、`PostgreSQL` 全部 0 结果，搜小写正常。三个模块同时受害，且**测试没覆盖大写输入**。

**修法**：`likePattern` 内 `.toLowerCase(Locale.ROOT)`（一处改，五处受益），并补一条大写关键词的用例。

### 11. 附件：上限漂移 + 类型完全由客户端决定

`chat/service/ChatAttachmentService.java:43`、`:64-67`、`:69`、`:79-83`

- `MAX_SIZE = 20MB`，但 `application.yml:25` 是 `max-file-size: 6MB`、`ChatAttachmentContextBuilder:44` 图片又是 5MB——**三处三个数字**。7~20MB 文件在进控制器前就被容器拒掉，提示"文件过大"却不说是 6MB。
- `store()` 不校验扩展名、MIME、魔数；`verify()` 原样保留客户端声明的 `filename`/`contentType`；`contentType.startsWith("image/")` 直接决定"是否 base64 送多模态模型"。把 `.exe` 标成 `image/png` 就会作为图片发给模型。知识库侧有白名单，聊天侧没有——**两条上传链路的信任模型不一致**。
- `:82` 把未清洗的原始文件名写进日志（`\n` 可伪造整行）。

**修法**：上限由同一个配置项驱动（容器 = 应用 + 余量）；`store()` 用服务端探测出的 contentType 落盘并维护允许列表；日志前清洗控制字符。

### 12. 分页页码整数溢出 → 稳定复现的 500

`common/api/PageDto.java:35`

```java
int from = effectivePage * effectiveSize;    // 21474837 * 100 溢出为负
... all.subList(from, ...)                   // IndexOutOfBoundsException → 500
```

`TaskQuery`/`KnowledgeDocumentQuery`/`CalendarEventService.search` 只把负 page 收敛为 0，没有上限。`GET /api/v1/tasks?page=21474837&size=100` 一条请求即可打 500。

**修法**：`long from = (long) page * size;` + `from >= all.size()` 返回空页 + page 加上限。

### 13. 客户端输入错误被兜底成 500

`common/exception/GlobalExceptionHandler.java:126-131`

只有 `Business`/`@Valid`/`ConstraintViolation`/`TypeMismatch`/`NoResource`/`MaxUploadSize` 六条，缺 `HttpMessageNotReadableException`（畸形 JSON）、`MissingServletRequestPartException`（上传不带 `file`）、`MissingServletRequestParameterException`、`HttpRequestMethodNotSupportedException`、`DataIntegrityViolationException`。全部落到 `Exception` 兜底 → **500 + `log.error` + 堆栈**，前端 401/500 拦截器误判为服务端故障，日志被客户端输入刷满。

**修法**：补三条 handler，统一映射 `VALIDATION_FAILED` / `METHOD_NOT_ALLOWED`；`DataIntegrityViolation` 单独映射成可读的 4xx（顺带修掉超长文件名导入 500）。

### 14. 对话页切会话有竞态，消息可能显示（甚至写进）错误的会话

`frontend/src/stores/chat.ts:145-178`

`selectSession` 先写 `currentConversationId`，再 `await listMessages` **无条件**赋给 `messages`。连点 A→B，若 A 后返回：标题是 B、内容是 A；此时 `send()` 取 `currentConversationId` 发消息 → 用户消息写进 B。另外 `:146-148` 在流式生成中直接 `return`，**静默无反应**，用户会以为点击失效而反复点。

**修法**：自增 `reqSeq` 或 `AbortController`，`await` 后校验 `id === currentConversationId` 再赋值；流式中给出明确提示或"先停止再切换"。

### 15. 「加载更早的消息」会把视图弹回最底部

`frontend/src/views/ChatView.vue:134-136`（watch `messages.length`）+ `:187-200`（`loadOlderMessages` 是头部插入）

`length` 一变就 `scrollToBottom()`，用户刚点"加载更早"立刻被甩到最新一条——这个功能实际上不可用。

**修法**：区分追加与前插；前插时记录 `scrollHeight` 差值补偿 `scrollTop`，watch 只在尾部 seq 变化时滚底，且用户已上滑时不自动滚底。

### 16. 首页统计数字是错的

`frontend/src/views/HomeView.vue:123-126` + `stores/task.ts:34-35`

`pendingCount/overdueCount` 是 `tasks`（**当前页，默认 20 条**）的派生值，首页直接当全量统计用；而 `taskStore.load()` 还会沿用上次的筛选条件。100 条待办时首页显示"≤20"，与任务页"共 100 条"自相矛盾。

**修法**：后端给聚合计数（`/tasks/stats` 或列表响应带 `statusCounts`），首页用它；不要复用分页列表的派生值。

### 17. 知识库"问答/检索"失败完全静默

`frontend/src/components/knowledge/KnowledgeAskTab.vue:17`、`KnowledgeSearchTab.vue:17,49`

两个 Tab 从不渲染 store 的 `error`（只有文档 Tab 渲染）。点"提问"转圈结束、页面什么都不变，用户分不清是失败还是没结果；检索 Tab 还把"还没搜"和"搜了没结果"合成同一个 `v-if="hits.length === 0"`。

**修法**：渲染 `el-alert`，检索用 `searched` 标志区分三态（`stores/search.ts:21` 已有这个模式可抄）。

**本轮踩到的两个「以为对、其实不对」**

1. **不能靠 `SseEmitter` 自带的 timeout 通知客户端。**
   最初在 `onTimeout` 回调里发 `error` 帧，集成测试显示：回调**确实执行了**、
   `send()` 也没抛异常，但客户端只收到 `start` 和第一条 `delta` 就 EOF ——
   因为 servlet 异步超时一旦触发，响应已被容器判为结束，再写什么都到不了对端。
   现在超时由我们自己的调度任务在连接仍活着时触发（`SseHeartbeatScheduler.scheduleOnce`），
   `SseEmitter` 的 timeout 只作兜底（比看门狗晚 5 秒）。
   **这个 bug 只有走真实 HTTP 的集成测试才能发现**，mock 掉 emitter 的单测会全绿。

2. **`@Transactional` 在同类内部自调用时静默失效。**
   拆分时第一版把 `claim` / `recordOutcome` 标成 `@Transactional(REQUIRES_NEW)` 并由
   `confirm` 调用 —— 走不到 Spring 代理，事务根本不存在，重构等于白做且看不出异常。
   改用 `TransactionTemplate`（与 `ChatSummaryService` 同一手法）。

**补丁 `8422041`：本轮自己引入的假超时告警**

上面第 12 项落地后，真机日志出现：一个 21:58:45 就 `done` 的会话，
在 22:00:45 报了一次 `流式对话超时（120000ms）`。原因是看门狗只在失败路径
（`stopEverything`）里被取消，**正常完成路径只停了心跳**。
数据没坏（`terminated` 的 CAS 挡住了后续动作），但每条成功对话都会刷一条假告警 ——
虚假告警会淹没真超时。

修法：正常完成路径补 `stop(watchdogRef.get())`，且看门狗任务自己先判 `terminated`
（「取消」与「已到点」会擦肩而过）。测试用 Spy 断言收尾时 `stop` 被调用两次，
并已回退修复验证该测试确实失败。

> **通用教训**：凡是注册了定时任务 / 监听器 / 订阅的地方，收尾时要**逐一核对是否都被取消**。
> 失败路径想到了、成功路径漏了，是最常见的漏法。这次是靠真机日志发现的，
> 单测和集成测试都覆盖不到（因为 CAS 让结果「看起来对」）。

**刻意不做（避免过度工程）**
- 不引入 WebFlux 重写流式链路——当前 `SseEmitter` 契约清晰、测试齐全，问题在写出口在哪个线程，不在框架。
- 不做虚拟滚动——个人库量级下每次 20 条足够；先修"翻历史被弹到底"这个真实痛点。
- 不上全量 CSRF token——单机自托管 + `SameSite=Lax` + 反代强制 HTTPS 的收益比远高于给所有写接口加 token 的复杂度；但应修正注释里不成立的那条理由。
- 不加 `@Size` 到 DTO——项目约定如此，长度校验走 `Texts`，改动应与现有风格一致而非另起一套。

## 五、附：值得保留的做法

审查中特意确认过、且**不建议在后续重构中改掉**的设计：

- 写操作一律经 Service，控制器不含业务逻辑；`PageDto` 的"排序只有一处真相"避免了 SQL 与内存 comparator 漂移。
- 幂等、确认、审计三层是**真的在跑**的：`operation_record` 唯一约束 + `ConfirmationRegistry` 启动期校验（缺处理器直接启动失败）+ 工具集合里没有确认类工具。
- MCP 的 fail-closed 策略与 schema 校验可靠；server 连不上时标记不可用照常启动，工具名冲突则启动失败。
- 前端安全面干净：`v-html` 仅一处且严格 `marked → DOMPurify`；`localStorage` 只存偏好；`target="_blank"` 带 `rel="noopener"`。
- 迁移只追加、`ddl-auto=validate`、向量维度启动期校验——这几条挡住了绝大多数"数据层静默损坏"。
