## 四、发现的问题（已在同日全部修复，见第十节）

### D1【P2·已复现】会话搜索传超大页码 → 稳定 500

```
GET /api/v1/chat/sessions/search?page=21474837&size=100   → 500
```

日志根因（`/tmp/backend-405.log`）：

```
org.springframework.dao.InvalidDataAccessApiUsageException:
  Page offset exceeds Integer.MAX_VALUE (2147483647)
  at PageableUtils.getOffsetAsInteger(PageableUtils.java:42)
  at SimpleJpaRepository.readPage(...) → findAll(spec, pageRequest)
```

`ChatSessionService.search` 把客户端传来的 `page` 直接交给 `PageRequest.of()`，
Spring Data 在生成 offset 时按 `int` 截断并抛异常 → 被 `Exception` 兜底成 500 + 完整堆栈。
`PageDto.of()` 早已用 `long` 计算并修掉了内存切片路径（审查文档第 12 条），
**但走 SQL 分页的会话搜索是另一条路径，没有被那次修复覆盖**。

- 影响：一个构造出来的查询参数即可打 500，日志里留一条假堆栈；
  搜索框被脚本/书签反复触发时会污染日志。
- 建议：`page` 在 DTO 层收敛上限（如 `min(page, 20000)`），或把
  `InvalidDataAccessApiUsageException` 映射为 400；两者都做更稳。
- 用例：`G2-15 分页极端值`（同名用例已固化，修好即转绿）。

### D2【P3】内容协商错误被降级成 500

```
GET /api/v1/chat/sessions/{id}/export   Accept: application/json  → 500
```

`HttpMediaTypeNotAcceptableException`（语义上应是 406）落到了 `Exception` 兜底。
这是审查文档第 13 条「客户端输入错误被兜底成 500」的同类漏项 ——
那次补了 `HttpMessageNotReadable` 等几条，**没补 `HttpMediaTypeNotAcceptable`**。

- 影响：只用 `Accept: application/json` 的客户端访问导出接口时看到「内部错误」，
  而真正原因只是内容协商不匹配。
- 建议：`GlobalExceptionHandler` 补一条 handler → 406 + `ApiErrorController` 的 JSON 错误体。

### D3【P2·口径矛盾】「预算」和「实际发送量」不是同一个分母

实测同一会话：

| 指标 | 数值 | 来源 |
|---|---|---|
| `GET /chat/sessions/{id}/context` | **103** tokens | 系统提示 + 历史字符，按 1.6 字/token 估算 |
| `done.promptTokens`（同一轮） | **4116** tokens | 上游 `usage.prompt_tokens`（含 23 个工具定义） |
| 预算设为 2048 时的实测 | 4992 / 5855 / 5865 | 连续三轮，**恒超预算 2.4~2.9 倍** |

两处差 40 倍。原因分两层：

1. **预算只裁历史字符**（`JpaChatMemory.selectWindow` → `effectiveCharBudgetFor`），
   系统提示与 **23 个工具的 schema** 不参与裁剪，而后者每轮都随请求发送，约 4000 token；
2. **仪表盘用字符估算、done 用上游真实 usage**，两个来源不同（`ChatPromptAssembler.estimateHistoryChars`
   还刻意忽略裁剪，注释写明「偏差方向偏大是安全的」）。

- 影响：用户设 2048 预算，界面显示「103 / 2048（5%）」，实际请求已发 4116 token；
  而小预算下 done 又会显示「4992 / 2048（243%）」。**两种显示都自相矛盾**，
  且预设在 32K 以下时预算基本无法约束真实占用。
- 建议：仪表盘与 done 统一口径（推荐都用上游 usage，并在 UI 上把「工具+系统开销」
  作为单独一项列出），或在估算里加一份工具 schema 的固定开销。

### D4【P3·契约不一致】附件名片在 `done` 之后才补写

`docs/api.md` 明确写「`done` 表示该落的库都落完了」。实测：收到 `done` 后
立刻 `GET /messages`，用户消息的 `attachments` 为 `[]`；等 200~600ms 后才出现
（`ChatTurnFinisher.afterDone` → `attachAttachments`）。

引用（citations）**刻意排在 done 之前**（代码注释写明理由），附件却在 done 之后 —— 两条链路不对称。

- 影响：严谨的客户端（收到 done 即刷新消息列表）会短暂看到「附件丢了」。
- 建议：把附件挂载移到 `attachCitations` 旁边，与引用同一时机。

### D5【P3·噪音】客户端中断每次留一条 ERROR 全堆栈

中断流式对话后日志出现：

```
ERROR ... GlobalExceptionHandler : 未捕获异常，已按内部错误处理
org.springframework.web.context.request.async.AsyncRequestNotUsableException:
  Servlet container error notification for disconnected client
Caused by: java.io.IOException: Broken pipe
```

这是用户主动取消（正常行为），却按「服务端故障」记 ERROR + 40 行堆栈。
- 建议：单独识别 `AsyncRequestNotUsableException` 并降到 DEBUG/INFO，否则真故障会被淹没。

## 五、验证通过的关键能力（带证据）

- **SSE 契约**：`start → delta* → done` 顺序与唯一性、`done.content` 等于全部 delta 拼接、`promptTokens > 0`、落库内容与 done 一致、序号连续。
- **中断**：读到第 3 个事件后断开，1.5 秒后查库 —— 只剩 1 条 USER 消息，**没有半截助手回答**。
- **多轮上下文**：第 1 轮「记住 7741」，第 2 轮问「刚才的数字」→ 答对。
- **工具调用真实落库**：模型说建就真的建了（`select count(*) from task` = 1），审计表有记录。
- **破坏性操作三重防护**：未确认前任务仍在 → 错令牌被拒且任务仍在 → 正确令牌 `executed=true, affectedCount=1` 且任务消失 → 另一条走取消，状态 `CANCELLED` 且任务仍在。
- **计划控制层**：多步任务触发 `createPlan`，`GET /conversations/{id}/plan` 返回步骤（本轮耗时 25s）。
- **RAG 全链路**：分块数 = 向量条数；独特标识符可命中；问答带 `[1]` 引用；对话 `citations` 事件在 `done` 之前且编号从 1 开始、快照落库；删除文档后向量清零且不再命中；**无关提问不编造**（拒答或明说没有）。
- **记忆是硬约束**：设为常驻后**新会话**问「我最常用什么语言」→ 答 Rust（证明不走相似度召回）；`hitCount` 累加。
- **边界值**：4000 字恰好通过、4001 字拒绝；预算 0/负数 400、超大收敛到 1M；topK 999 收敛；思考档位乱填回落 off。
- **限流**：70 次突发中后段返回 429 且 `code=42900`，且限流前的请求正确返回 404（限流不掩盖真实错误）。
- **空库零故障**：健康检查 UP、列表 `[]`、不存在资源一律 404 信封且不含堆栈。

## 六、本轮覆盖不到的盲区（建议下一轮补）

1. **登录与鉴权**：`AUTH_ENABLED=false`，401/会话过期/CSRF 全未验证 —— 公网开放前必须补。
2. **流式超时（120s）与看门狗**：需要构造慢端点，本轮未测。
3. **MCP 真实连接**：当前 `enabled=false`、无 server，只验证了「无配置时返回空清单」。
4. **图片多模态**：只验证了图片类文件能上传与取回，未验证模型真的读图。
5. **前端渲染**：本轮全部走 HTTP 契约；942 条前端断言是纯函数级，没有 DOM 渲染测试。
6. **多用户/跨设备**：单用户设计，并发只测了「同一会话两条消息不产生 5xx」。

## 八、本轮对用例本身的 6 处校正（避免把正确设计判成缺陷）
