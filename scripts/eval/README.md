# 检索评测（R@1/3/5 · MRR · 多样性）

> 建立时间：2026-10-25。动机见下 —— **没有这个之前，任何调参都无法验证是否真的变好。**

## 为什么需要它

单元测试里的嵌入模型是确定性词袋实现，向量库是真的，所以自动化测试能验证
「流程通不通」，验证不了「排得准不准」。而「准不准」此前只能靠感觉。

这个目录把「准不准」变成可重复的数字。

## 组成

| 文件 | 作用 |
|---|---|
| `fetch-corpus-juejin.py` | 抓取第一批语料（10 篇） |
| `fetch-corpus-batch3.py` | 抓取第二批语料（16 篇，扩到 26 篇以打破 R@5 天花板；curl 被反爬后改用浏览器，见下） |
| `rebuild-corpus.py` | 清空知识库并按**当前**切分策略重新入库（切分策略变了就必须重建，否则对比无效） |
| `queries.py` | **查询集（129 条）**，分 term / natural / cross 三档难度，逐条标注可接受文档 |
| `retrieval-eval.py` | 跑查询集，输出 R@1/3/5、MRR、文档多样性，并按难度/文档分组 |
| `noise-floor.py` | 测量「同一查询重复请求」的得分漂移，为判平阈值提供依据 |
| `fetch-corpus-browser.js` | 用 Playwright 绕过掘金反爬（curl 被抓 ~8 篇后会撞 JS 挑战页） |
| `to-markdown.py` | 把浏览器抓到的 HTML 片段转 Markdown（与 curl 路径共用同一套规则） |

语料 post id 与查询标注都写死在脚本里。**换语料必须同步改标注**，
否则数字没有意义。

## 用法

```bash
# 1. 语料（已抓过会跳过）
python3 scripts/eval/fetch-corpus-juejin.py    # 第一批 10 篇
python3 scripts/eval/fetch-corpus-batch3.py    # 第二批 16 篇

# 掘金反爬：curl 连续抓 ~8 篇后会被 argus-csp-token 的 JS 挑战页拦（响应只剩 2.5KB）。
# 等待无效（挑战要执行 JS），必须改用真实浏览器：Playwright 拿 .article-viewer 的
# innerHTML 落盘，再由 to-markdown.py 转 Markdown（与 curl 路径共用同一套转换规则）。

# 2. 起后端后重建知识库（会先删掉全部现有文档）
python3 scripts/eval/rebuild-corpus.py

# 3. 评测（加 -v 看每条的 top5 明细）
python3 scripts/eval/retrieval-eval.py

# 4. 需要重新确认判平阈值时（换嵌入模型后应重跑）
python3 scripts/eval/noise-floor.py
```

## 查询集：129 条里的三档难度

| level | 条数 | 含义 | 举例 |
|---|---|---|---|
| `term` | 24 | 查询直接用术语，与文档有明确词面重叠 | 「BRIN 索引适合什么场景」 |
| `natural` | 22 | 自然问句，措辞不同但共享关键词 | 「索引在什么情况下会失效」 |
| `cross` | 83 | **刻意避开术语**，用意图/现象描述 | 「日志表按时间顺序写入，该建什么索引」 |

`cross` 占 64%，因为**只看 `term` 会严重高估检索能力** —— 词袋式实现能通过 term，
但过不了 cross。实测也印证：term 档 R@1 95.8%，cross 档只有 77.1%。

27 条给了 2~3 篇可接受文档（同主题重叠），命中任一都算对。
**双标注前逐篇 `grep` 核实过关键词归属**，不是凭印象加。

### 标注的一个坑：关键词出现 ≠ 那篇能回答

有 3 条查询的关键词确实出现在别的文档里，但语义完全不同，因此**不能**加进标注：

| 关键词 | 误判对象 | 实际含义 |
|---|---|---|
| `watch` | TypeScript 类型体操 | `Watcher<T>` 是个类型名，不是 Vue 的 `watch` |
| `unknown` | TypeScript 泛型与条件类型 | `T extends unknown` 讲的是分发，不是 unknown vs any |
| `ip_hash` | Nginx 完整配置参考手册 | 只是配置模板里的一行注释，没讲副作用 |

只看 grep 命中数会把它们标错，进而把「检索对了」判成「失败」。

## 当前基线（2026-10-26 v3：混合检索 / 26 篇 / 233 分块 / 129 条查询）

| 指标 | 混合检索 | 判平后 | 纯向量（对照） | 随机基线 |
|---|---|---|---|---|
| R@1 | **86.0%** | — | 81.4% | 3.8% |
| R@3 | **96.9%** | — | 93.8% | 11.5% |
| R@5 | **96.9%** | — | 95.3% | 19.2% |
| MRR | **0.910** | — | 0.875 | — |
| 未命中 | **4/129（3.1%）** | — | 6/129（4.7%） | — |

> 混合检索下**判平指标自动跳过**（排序由 RRF 而非 cosine 决定，见「混合检索」一节的副作用说明），
> 因此不再列判平列。纯向量模式仍可看判平（82.2%）。

3 次连续运行的波动：R@3、R@5 完全稳定（极差 0）；R@1 极差 0.8%（1 条查询，属噪声）。
「纯向量」一列是同一时刻关闭 `AI_KNOWLEDGE_HYBRID_ENABLED` 跑出来的真 A/B，不是历史数字。

### 这批数字终于有区分力了

上一版语料只有 10 篇，R@5 恒为 100%（随机基线 50%，天花板效应）。
扩到 26 篇后随机基线降到 19.2%，R@5 落到 95.3% —— **指标才开始能反映差异**。

**与 10 篇版本的分数不可直接比较**：语料大 2.6 倍、cross 档占比从 56% 升到 64%，
是更难的测试。R@1 从 84.2% 降到 81.4% 不代表退化。

### 6 条未命中：全是真失败，成因高度一致

逐条核实过「期望文档是否唯一含该关键词」：

| 查询 | 期望 | 关键词是否只在期望文档 |
|---|---|---|
| watch 的回调什么时候执行 | Vue3 响应式 | 是（TS 那篇只有 `Watcher<T>`，语义不同） |
| 死循环为什么不饿死其他协程 | GMP 调度器 | 是 |
| unknown 和 any 到底差在哪 | TS 类型体操 | 是（泛型篇的 `T extends unknown` 讲的是分发） |
| 2PC 有什么问题，3PC 改进了什么 | 系统性理解分布式 | 是 |
| 跨多个服务的长事务…用什么模式 | 系统性理解分布式 | 是（Saga） |
| 同一 IP 哈希分配会有什么副作用 | Nginx 生产优化 | 是（手册篇只是注释里提了一句） |

两类根因，都不是切分或去重能解决的：

1. **精确标识符 / 短英文词**：`watch`、`unknown`、`any`、`2PC`、`3PC`、`ip_hash`。
   这类 token 在嵌入空间里几乎没有语义，向量检索天然弱。
2. **跨域概念**：「锁」「事务」「调度」「哈希」「饿死」在多个领域都存在，
   嵌入模型分不清「MySQL 的行锁」和「分布式锁」。

这两类正是**混合检索（向量 + 全文关键词兜底）**要解决的场景 ——
关键词能精确命中 `3PC` 这种 token，向量擅长语义词，两者互补。

### 噪声底随语料规模上升

`noise-floor.py` 两次测量对比：

| 语料 | 标准差中位数 | 极差 P90 | 极差 max | 建议阈值 |
|---|---|---|---|---|
| 10 篇 | 0.0005 | 0.0029 | 0.0048 | 0.005 ~ 0.006 |
| 26 篇 | 0.0009 | 0.0035 | 0.0082 | **0.007** |

语料越大，候选越多、近并列越多，噪声底越高。**改语料后必须重跑 `noise-floor.py`**
并更新 `NOISE_TOLERANCE`，否则判平会失效。

### 多分块文档仍然容易占位（但已好很多）

按文档的「首答率」显示两类弱项：

- `系统性地理解分布式系统`（8 块）：5/7 命中、首答 4 —— 两篇分布式文档互相抢位。
- `GMP 调度器`（5 块）：4/5 命中、首答仅 2 —— 被 Go 并发模式与 Python 异步篇压制。
- `Vue3 响应式`（**仅 1 块**，1203 字符）：4/5 命中、首答 3 —— 全文只有一块，
  一旦这块的向量不够突出，整篇就沉底。这是**短文档的结构性劣势**。

## 关于 Precision@5：不用它

每个查询只标注 1~2 篇相关文档，Precision@5 的理论上限只有 0.2~0.4，数值没有意义。
更要紧的是：在「按片段取 topK」的实现下，同一文档的重复片段会把它刷高
（出现 4 次 = 0.8），等于**奖励重复**。

2026-10-25 引入文档级去重后，这个指标从 48% 掉到 19%，而检索质量实际是变好的 ——
正是这个缺陷的证明。替代指标用**文档多样性** = top5 里不同文档数 / 5。

## 基线演进

| 版本 | 语料 | 查询 | R@1 | R@5 | 关键变化 |
|---|---|---|---|---|---|
| ① | 10 篇 + 3 样例 | 20 | — | 95% | 固定 token 切分，无去重 |
| ② | 10 篇 + 3 样例 | 20 | — | 95% | 结构切分 + 去重（**有丢块 bug**） |
| ③ | 10 篇 | 20 | 80% | 100% | 修丢块 + 拒收短文档 + 去重 |
| ④ | 10 篇 | 57 | 84.2% | 100% | 查询分档 + 判平指标 |
| ⑤ | **26 篇** | **129** | **81.4%** | **95.3%** | 扩语料打破天花板 |

**①②③ 的 R@5 用旧口径（未判平、标注较松），④⑤ 用新口径，横向不可直接比。**
真正可比的是「同一语料 + 同一查询集」前后：③→④ 是同语料改指标口径，
④→⑤ 是改语料（更难）。

② 那一列留在表里是因为它证明了一件重要的事：指标看起来「还行」的时候，
可能正在丢一半内容 —— 见下面的 bug 记录。

## 三项改进（2026-10-25）

1. **入库过滤过短文档**：低于 `min-chunk-size-chars`（350）的文档直接拒收。
   源头拒收比在检索端过滤干净 —— 原本 29 / 92 字符的样例文档会因向量信号过于
   「集中」而挤进前 5。
2. **检索按文档去重**：多取 3 倍片段 → 每篇只留最高分那条 → 按文档分排序 → 截到 topK。
   这解决「一篇 13 块的文档一次占掉 3–4 个位置」，文档多样性 51% → 78%。
3. **结构感知切分**（替换固定 token 切分）：按标题分节、保留章节路径前缀
   （`【章节：A > B】`）、超长节按段落切、兜底按**字符**在句末断开。
   固定 token 切分会把一句话从中间劈开，且块不带任何结构信息。

## 切分改造中踩到的两个 bug（都靠数据发现，不靠读代码）

**1. 前缀叠加**：先给每块加章节前缀、再合并短块，导致一个块里嵌进 3 个
`【章节：…】` —— 白占 token，还让嵌入混入互不相关的章节名。
修法：先产出不带前缀的片段并合并，最后统一加一次前缀。

**2. 静默丢块（最严重）**：合并短块时先 `remove` 再判断体积上限，
超限时前一块**既不回列表也没被加入**，直接消失。
实测 `HTTP 渐进` 原文 13867 字符只索引了 7173（丢 48%），
而与此同时 Recall@5 仍是 95% —— 指标完全没报警。

修法：先 `peek` 再决定。并补了「内容守恒」测试：
断言产出块的总字符数不少于原文的 95%，以及每个标记字符出现次数守恒。

> **这个 bug 是本轮最重要的产出。** 它说明：只看检索指标不够，
> 还要有一条「切分不丢内容」的不变量做守门。

## 混合检索（2026-10-26）

向量通道 + 关键词通道，用 RRF 融合。开关：`AI_KNOWLEDGE_HYBRID_ENABLED`。

### 效果（129 条查询 / 26 篇语料 / 同一时刻 A/B）

| 模式 | R@1 | R@3 | R@5 | MRR | 未中 |
|---|---|---|---|---|---|
| 纯向量（基线） | 81.4% | 93.8% | 95.3% | 0.875 | 6 |
| **混合（最终）** | **86.0%** | 96.9% | 96.9% | **0.910** | 4 |
| 差值 | **+4.6pp** | +3.1pp | +1.6pp | +0.035 | −2 |

逐条对比（9 条变好 / 2 条变差，主要变好项）：

| 查询 | 纯向量 | 混合 |
|---|---|---|
| unknown 和 any 到底差在哪 | 未中 | **@1** |
| 2PC 有什么问题，3PC 改进了什么 | 未中 | **@2** |
| watch 的回调什么时候执行 | 未中 | **@2** |
| void 和 undefined 是同一个东西吗 | @4 | **@1** |

### 五个变体的完整对比（这次调参是本轮最重要的记录）

| 变体 | R@1 | R@5 | 未中 | 结论 |
|---|---|---|---|---|
| 子串 + 同权（无 IDF） | 85.3% | 97.7% | 3 | 指标不错，但 io 噪声未受控 |
| 词首正则 + 同权 | 82.9% | **98.4%** | **2** | R@5 最好，R@1 掉 2.4pp |
| 词首 + IDF + 0.5 权 | 83.7% | 96.1% | 5 | 最差，两个收紧叠加过头 |
| 子串 + IDF + 0.5 权 | 84.5% | 96.1% | 5 | 降权把该救的也压掉了 |
| **子串 + IDF + 同权** | **86.0%** | 96.9% | 4 | **最终选择** |

### 三个被数据推翻的直觉

**1. 「词首匹配能减少噪声」→ 但它同时砍掉了召回。**
`ILIKE '%io%'` 在 233 个片段里命中 118 个（51%），因为 `version`、`configuration`
里都含 `io`。改用词首 `~* '\mio'` 后只命中 7 个 —— 噪声确实没了，
但 R@1 从 85.3% 掉到 82.9%。正确做法是**宽召回 + IDF 抑制**，而不是收紧匹配。

**2. 「关键词通道要降权，否则它的 top1 会压掉正确答案」→ 数据否定。**
我据此把默认权重设成 0.5，结果 R@1 84.5% / 未中 5，比同权的 86.0% / 未中 4 更差。
压权重把「本该被关键词救回」的查询一起压没了。**真正的噪声抑制手段是 IDF，不是整体降权。**

**3. 「df 统计可以用词首、检索用子串」→ 不自洽会让 IDF 失效。**
`io` 的词首 df=7（3%）vs 子串 df=118（51%）。用词首统计时 IDF 以为它很稀有、
给了接近 1 的权重，噪声完全没被压住。**统计口径必须与检索口径完全一致。**

### 已知副作用

- **仅关键词命中的片段 `score` 为 null**：它没做过嵌入，不能编分数。
  API 加了 `matchedBy`（VECTOR / KEYWORD / BOTH），前端据此显示「关键词命中」而非「—」。
- **判平指标在混合检索下自动跳过**：判平的前提是「排序由 score 决定」。
  RRF 排序与 cosine 不再单调对应，若仍按 score 判平会得出「判平后比严格更差」的荒谬结果
  （实测出现）。脚本现在检测 score 序列是否单调，不单调就退回严格名次。
- **纯中文查询走不到关键词通道**：`KeywordExtractor` 只提取英文/数字 token。
  中文语义交给向量 —— 这是刻意的边界。因此 3 条仍未命中的查询全是纯中文跨域概念
  （「死循环为什么不饿死其他协程」「跨多个服务的长事务…用什么模式」），
  混合检索救不了，需要更强的嵌入模型或 rerank。

### 实现要点

| 组件 | 职责 |
|---|---|
| `KeywordExtractor` | 从查询提取英文/数字 token（≤3 个），过滤停用词；**数字开头要保留**（`2PC` 不能被截成 `PC`） |
| `VectorStoreInspector.searchByKeyword` | 单 token 子串检索（`ILIKE` + `ESCAPE`） |
| `VectorStoreInspector.countBySubstring` | df 统计，**口径与检索一致** |
| `KnowledgeRetrievalService` | 每 token 一路通道，`1/(k+rank) × IDF × 通道权重` 累加后融合 |

**为什么每个 token 单独一路**：拼成一条 OR 查询会丢失「哪个 token 命中」的信息，
而 `unknown`（df=8）与 `ip`（df=13）的可信度本就不同，分开才能按 IDF 区别对待。
