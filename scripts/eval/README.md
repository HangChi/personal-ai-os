# 检索评测（Recall@5）

> 建立时间：2026-10-25。动机见下 —— **没有这个之前，任何调参都无法验证是否真的变好。**

## 为什么需要它

单元测试里的嵌入模型是确定性词袋实现，向量库是真的，所以自动化测试能验证
「流程通不通」，验证不了「排得准不准」。而「准不准」此前只能靠感觉。

这个目录把「准不准」变成可重复的数字。

## 组成

| 文件 | 作用 |
|---|---|
| `fetch-corpus-juejin.py` | 抓取语料（10 篇掘金文章，主题刻意错开，MySQL/Go/HTTP 各 2 篇形成同主题干扰） |
| `retrieval-eval.py` | 跑 20 个已标注查询，输出 Recall@5 / MRR / Precision@5 / Accuracy@1 |

语料 post id 与查询标注都写死在脚本里。**换语料必须同步改标注**，
否则数字没有意义。

## 用法

```bash
# 1. 语料（已抓过会跳过；掘金对连续请求会反爬，失败会主动停）
python3 scripts/eval/fetch-corpus-juejin.py

# 2. 上传全部文章到知识库（或用知识库页面逐个上传）

# 3. 起后端后跑评测
python3 scripts/eval/retrieval-eval.py
```

## 基线（2026-10-25，10 篇掘金 + 3 个样例文档，共 69 个分块）

| 指标 | 值 |
|---|---|
| **Recall@5** | **19/20 = 95.0%** |
| MRR | 0.846 |
| Precision@5 | 48.0% |
| Accuracy@1 | 16/20 = 80.0% |

### 读这些数字时的两个已知偏差

1. **Recall@5 偏高**：同主题有 2 篇文档（MySQL / Go / HTTP），主题词高度重叠，
   命中另一篇也算「沾到主题」。严格说这是指标固有偏差，不是实现有多好。
2. **Precision@5 偏低**：同一个偏差的反面 —— top5 里出现的同主题另一篇不在标注里。

两个偏差方向相反、互相制衡，所以要**一起看**。

## 失败案例（比总分更有信息量）

1. **「computed 是怎么做缓存的」完全未命中 Vue3**，top5 全是 Redis/HTTP。
   词义冲突：「缓存」在 Redis 那篇里是全文主题，在 Vue3 那篇只出现一次
   （且全文仅 1203 字符、1 个分块）。模型分不清两种语境的「缓存」。
2. **极短样例文档反复进入 top5**：`vocab`（29 字符）、`sample`（92 字符）
   在 3 个查询里挤进前 5。短文档的向量信号过于"集中"，与短查询的相似度反而高。
3. **多分块文档霸占 topK**：`HTTP 渐进`（10 块）、`MySQL 事务`（13 块）
   经常一次占掉 3–4 个位置，把只切出 1–3 块的正确文档挤出榜。
   因为 topK 是按**片段**取的，不是按**文档**。

## 由此得出的改进候选（按性价比）

| # | 改进 | 针对问题 | 预期 |
|---|---|---|---|
| 1 | 入库前过滤过短文档（低于 `min-chunk-size-chars` 的不入库） | 问题 2 | 立竿见影，无风险 |
| 2 | 检索按**文档**去重（每文档取最高分片段，再按文档分排序取 topK） | 问题 3 | 显著提升 Precision，Recall 基本不变 |
| 3 | 建更大评测集（50+ 查询）后再谈调阈值 | 全部 | 样本 20 的置信区间太宽，±0.1 都可能 |

**改动后必须重跑本脚本对比**，否则无法区分「真的变好」与「感觉变好」。
