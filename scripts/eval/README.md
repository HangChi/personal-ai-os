# 检索评测（Recall@5）

> 建立时间：2026-10-25。动机见下 —— **没有这个之前，任何调参都无法验证是否真的变好。**

## 为什么需要它

单元测试里的嵌入模型是确定性词袋实现，向量库是真的，所以自动化测试能验证
「流程通不通」，验证不了「排得准不准」。而「准不准」此前只能靠感觉。

这个目录把「准不准」变成可重复的数字。

## 组成

| 文件 | 作用 |
|---|---|
| `fetch-corpus-juejin.py` | 抓取语料（10 篇掘金文章，主题刻意错开，MySQL/Go/HTTP 各 2 篇形成同主题干扰） |
| `rebuild-corpus.py` | 清空知识库并按**当前**切分策略重新入库（切分策略变了就必须重建，否则对比无效） |
| `queries.py` | **查询集（57 条）**，分 term / natural / cross 三档难度，逐条标注可接受文档 |
| `retrieval-eval.py` | 跑查询集，输出 R@1/3/5、MRR、文档多样性，并按难度/文档分组 |
| `noise-floor.py` | 测量「同一查询重复请求」的得分漂移，为判平阈值提供依据 |

语料 post id 与查询标注都写死在脚本里。**换语料必须同步改标注**，
否则数字没有意义。

## 用法

```bash
# 1. 语料（已抓过会跳过；掘金对连续请求会反爬，失败会主动停）
python3 scripts/eval/fetch-corpus-juejin.py

# 2. 起后端后重建知识库（会先删掉全部现有文档）
python3 scripts/eval/rebuild-corpus.py

# 3. 评测（加 -v 看每条的 top5 明细）
python3 scripts/eval/retrieval-eval.py

# 4. 需要重新确认判平阈值时（换嵌入模型后应重跑）
python3 scripts/eval/noise-floor.py
```

## 查询集：57 条里的三档难度

| level | 条数 | 含义 | 举例 |
|---|---|---|---|
| `term` | 7 | 查询直接用术语，与文档有明确词面重叠 | 「BRIN 索引适合什么场景」 |
| `natural` | 18 | 自然问句，措辞不同但共享关键词 | 「索引在什么情况下会失效」 |
| `cross` | 32 | **刻意避开术语**，用意图/现象描述 | 「日志表按时间顺序写入，该建什么索引」 |

`cross` 占 56%，因为**只看 `term` 会严重高估检索能力** —— 词袋式实现能通过 term，
但过不了 cross。

## 当前基线（2026-10-26，57 条查询 / 10 篇文档 / 68 分块）

| 指标 | 严格 | 判平后 |
|---|---|---|
| R@1 | 84.2%（轮间波动 84.2%~86.0%） | 86.0%（3 次运行稳定） |
| R@3 | 100.0% | 100.0% |
| R@5 | 100.0% | 100.0% |
| MRR | 0.912 | 0.924 |
| 文档多样性 | 79.3% | — |
| 未命中 | 0 | — |

按难度（严格 R@1）：term 100% · natural 83.3% · cross 81.2%

### ⚠️ R@5 = 100% 是天花板效应，不是「检索完美」

语料只有 **10 篇**，topK=5 按文档去重后等于「取前一半」。**即便检索完全随机，
R@5 的期望也是 50%，R@3 是 30%，R@1 是 10%。**

所以「R@5 = 100%」只说明「正确答案总在前一半」——弱结论。
真正有区分度的是 **R@1（84.2%，随机基线 10%，约 8.4 倍）**。
要让 R@5 具备区分力，语料至少要扩到 25~30 篇（随机基线降到 17~20%）。

### ⚠️ 得分本身不可复现：噪声底 0.006

`noise-floor.py` 实测（12 条查询 × 5 次，两次测量）：同一查询文本重复请求，
同一文档的得分**标准差中位数 0.0005~0.0006、极差 P90 0.0024~0.0029、max 0.0048**。

这说明嵌入向量不是逐位可复现的（模型侧数值非确定性，不是代码问题）。后果：

1. **两次跑同一份查询集，R@1 可能差一两条**。实测 6 次全量运行中，
   严格 R@1 出现过 84.2% 与 86.0%（差 1 条查询）；
2. **得分差小于 0.006 的两篇文档，谁在前是抽样决定的**，谈不上排序错误。
   最典型的是「ref 和 reactive 该用哪个」：Vue3 与 HTTP 两篇在 5 次重复请求里
   互换过名次，得分差仅 0.0009。

因此 `retrieval-eval.py` 除了严格指标，还报一份**判平后**指标：
只统计「显著高于正确答案」（得分差 > 0.006）的文档数。
实测判平后 R@1 在 3 次连续运行中稳定为 86.0% —— **A/B 比较请以判平后指标为准**，
否则会把噪声当成改进。

## 9 条非首选的实际成因（逐条核实过，不是猜的）

| 成因 | 条数 | 说明 |
|---|---|---|
| **真失败** | 4 | 正确答案所在文档是**唯一**含该关键词的，仍被别的文档压过 |
| 统计并列 | 1 | 得分差 0.0009，在噪声内 |
| 标注缺口 | 4 | 获胜文档其实也能回答，是我标注只写了一篇 |

真失败这 4 条值得单独看，它们揭示的是**跨域语义混淆**：

| 查询 | 期望 | 实际压过它 | 关键词只在期望文档出现？ |
|---|---|---|---|
| 只给未完成的订单建索引 | PostgreSQL | MySQL 事务 | 是（未完成/部分索引） |
| watch 的回调什么时候执行 | Vue3 | Go 并发模式 | 是（watch） |
| 死循环为什么不饿死其他协程 | GMP | MySQL 事务 | 是（饿死） |
| 并行度配额的数量由什么决定 | GMP | Go 并发模式 | 是（并行度） |

共性：**「调度」「饿死」「并行度」这类概念在多个领域都有，嵌入模型跨不过去。**
这不是切分或去重能解决的，属于嵌入模型的能力边界 —— 该上混合检索（关键词兜底）
或更好的嵌入模型。

标注缺口那 4 条（`索引会失效` / `强缓存协商缓存` / `OR 条件` / `网络 IO 阻塞`）
说明一件事：**同主题多篇文档时，「正确答案」本来就不唯一**，
标注只写一篇会把正确命中判成失败。若要更严谨，应扩成「相关性分级」标注。

## 关于 Precision@5：不用它

每个查询只标注 1~2 篇相关文档，Precision@5 的理论上限只有 0.2~0.4，数值没有意义。
更要紧的是：在「按片段取 topK」的实现下，同一文档的重复片段会把它刷高
（出现 4 次 = 0.8），等于**奖励重复**。

2026-10-25 引入文档级去重后，这个指标从 48% 掉到 19%，而检索质量实际是变好的 ——
正是这个缺陷的证明。替代指标用**文档多样性** = top5 里不同文档数 / 5。

## 基线演进

语料固定为 10 篇掘金文章；三次测量分别在三个实现状态下。

| 指标 | ① 固定 token 切分 | ② 结构切分 + 去重（有 bug） | ③ 修复后（当前） |
|---|---|---|---|
| R@5 | 95% | 95% | **100%** |
| MRR | 0.846 | 0.875 | **0.912** |
| 文档多样性 | 51% | 78% | **79.3%** |
| 分块数 | 56 | 72 | 68 |
| 内容守恒 | ✅ | ❌ 只索引了 55%（丢块 bug） | ✅ |

② 那一列是**中间态**，留在表里是因为它证明了一件重要的事：
指标看起来「还行」的时候，可能正在丢一半内容 —— 见下面的 bug 记录。

## 三项改进（2026-10-25）

1. **入库过滤过短文档**：低于 `min-chunk-size-chars`（350）的文档直接拒收。
   源头拒收比在检索端过滤干净 —— 原本 29 / 92 字符的样例文档会因向量信号过于
   「集中」而挤进前 5。
2. **检索按文档去重**：多取 3 倍片段 → 每篇只留最高分那条 → 按文档分排序 → 截到 topK。
   这解决「一篇 13 块的文档一次占掉 3–4 个位置」，文档多样性 51% → 78%。
3. **结构感知切分**（替换固定 token 切分）：按标题分节、保留章节路径前缀
   （`【章节：A > B】`）、超长节按段落切、兜底按**字符**在句末断开。
   固定 token 切分会把一句话从中间劈开，且块不带任何结构信息。

## 切分改造中踩到的两个 bug（都靠数据发现，不靠读代码）

**1. 前缀叠加**：先给每块加章节前缀、再合并短块，导致一个块里嵌进 3 个
`【章节：…】` —— 白占 token，还让嵌入混入互不相关的章节名。
修法：先产出不带前缀的片段并合并，最后统一加一次前缀。

**2. 静默丢块（最严重）**：合并短块时先 `remove` 再判断体积上限，
超限时前一块**既不回列表也没被加入**，直接消失。
实测 `HTTP 渐进` 原文 13867 字符只索引了 7173（丢 48%），
而与此同时 Recall@5 仍是 95% —— 指标完全没报警。

修法：先 `peek` 再决定。并补了「内容守恒」测试：
断言产出块的总字符数不少于原文的 95%，以及每个标记字符出现次数守恒。

> **这个 bug 是本轮最重要的产出。** 它说明：只看检索指标不够，
> 还要有一条「切分不丢内容」的不变量做守门。
